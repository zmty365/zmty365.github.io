Kubernetes List-Watch 机制详解：从 client-go 到 Informer

发表于2026-08-07|Kubernetes
|总字数:2.6k|阅读时长:9分钟|浏览量:

上一篇讲了控制器的三大核心机制（声明式管理、控制循环、事件驱动），其中「事件驱动」能够高效落地，靠的正是底层的 List-Watch 机制。本文自底向上梳理：基于 List-Watch 的控制器架构、List & Watch 的概念与实践，以及在其之上封装的 Informer 机制。

一、基于 List-Watch 机制的控制器架构

1. 架构梳理

默认情况下，所有节点的 kubelet、master 节点的 scheduler（调度器）、controller-manager（控制管理器）都采取 list-watch 机制。

可以总结以下几点：

  • kubelet、scheduler、controller 都采取 list-watch 机制。
  • 这三个组件在启动时都要先 list 一次。
  • 随后当做出一个动作（例如删除、扩容、缩容）时，都会经过类似的几步：
    • api-server 收到命令，与底层的 etcd 交互，存储信息。
    • etcd 处理完后上报 api-server。
    • 上层的组件（包括用户）不断 watch，了解变化后做出相应的动作，再反馈给 api-server。

2. client-go

client-go 是 Kubernetes 官方提供的一个用于与 Kubernetes API 服务器进行交互的 Go 语言客户端库。它封装了与 Kubernetes API 服务器通信的底层细节，提供了简洁易用的 API 接口，让开发者可以方便地在 Go 语言程序中实现对 Kubernetes 集群资源（如 Pod、Service、Deployment 等）的创建、读取、更新和删除（CRUD）操作，以及对资源变化的监听等功能。

client-go 中负责向 api-server 发起 list-watch 的核心组件是 reflector。

其具有以下优势：

  • 简化开发：通过提供高层次的抽象和封装，开发者无需关心与 API 服务器通信的具体 HTTP 请求和响应细节，降低了开发与 Kubernetes 交互程序的难度。
  • 支持多种操作：支持对 Kubernetes 各种资源对象的操作，包括但不限于创建、查询、修改和删除，同时还支持对资源的事件监听（如 List-Watch 机制）。
  • 多版本兼容性：能够处理不同版本的 Kubernetes API，保证在不同版本的 Kubernetes 集群中都能正常工作。

client-go 并不属于 kubelet、scheduler 或 controller，但它们都会使用 client-go 库来与 Kubernetes API 服务器进行通信。

二、List & Watch

1. 基础概念

  • List：对应 Kubernetes API 的 list 操作，一次性获取某类资源的全量列表（例如获取某个 namespace 下的所有 Pod）。它是「拉取快照」，返回后连接即结束。
  • Watch：对应 Kubernetes API 的 watch 操作，与 API Server 建立一个长连接，持续接收资源的增量变化事件（新增、修改、删除），从而实时感知集群状态变化。

两者配合使用：先用 List 拿到全量数据作为初始状态（并记录当时的 resourceVersion），再从这个版本开始 Watch 增量事件，既保证了初始数据的完整性，又保证了后续变化的实时性。

Watch 返回的事件类型主要有：

  • ADDED：资源被新增。
  • MODIFIED：资源被修改。
  • DELETED：资源被删除。
  • BOOKMARK：书签事件，用于告知客户端当前最新的 resourceVersion，便于断线重连。
  • ERROR：出现错误。

2. 为什么重要

  • 实时性：相比轮询（不断重复 List），Watch 通过长连接推送变化，能第一时间感知集群状态，延迟更低。
  • 低开销：List 只在初始化时拉一次全量，后续只传输增量事件，大幅降低 API Server 与网络的压力。
  • 一致性基础：借助 resourceVersion，客户端可以在断线后从上次的位置续接，避免漏掉事件或重复处理。

三、Informer 机制

直接使用 List-Watch 虽然可行，但存在一些痛点：每个组件都自己维护一份数据、频繁访问 API Server、断线重连和缓存一致性都要自己处理。为此，client-go 在 List-Watch 之上封装了 Informer 机制。

Informer 可以理解为 List-Watch 的「加强版」，它在内部完成了以下工作：

  • 本地缓存（Local Store / Indexer）：Informer 通过 List-Watch 把资源数据同步到本地内存缓存中，之后的读取（如 Get、List）直接命中本地缓存，无需每次都请求 API Server。
  • 事件驱动回调：通过 ResourceEventHandler 注册 AddFunc、UpdateFunc、DeleteFunc 回调，当资源发生变化时自动触发对应处理逻辑，天然契合控制器的「事件驱动」模式。
  • 减少 API Server 压力：多个控制器可以共享同一个 SharedInformer，只维护一份 List-Watch 连接和一份缓存，避免重复拉取。
  • 自动重连与重新同步：底层的 reflector 负责发起 List-Watch，断线后会自动重连；Informer 还支持周期性的 Resync，保证本地缓存与实际状态最终一致。

它们之间的关系可以概括为：reflector 负责发起 List-Watch 拉取数据，Informer 在其上封装出本地缓存与事件回调，供上层控制器使用。

    A[API Server] -->|List 全量 + Watch 增量| B[Reflector]
    B --> C[本地缓存 Store/Indexer]
    B --> D[事件分发]
    D --> E[AddFunc]
    D --> F[UpdateFunc]
    D --> G[DeleteFunc]
    C --> H[控制器读取缓存]

（一）Informer 内部核心组件与数据流

上面的图是 Informer 的简化视角。实际上 client-go 的 Informer 内部由几个协作的组件构成，数据在它们之间单向流转：

  • Reflector：真正对 API Server 发起 List-Watch 的组件。它先 List 拿到全量对象，再 Watch 持续接收增量事件，并把这些变化包装成「Delta（变化增量）」放入 DeltaFIFO。
  • DeltaFIFO：一个先进先出的队列，按对象 key 聚合它的变化历史（Added / Updated / Deleted / Sync 等）。它是「数据入口」到「本地缓存」之间的缓冲区，保证事件按顺序被消费。
  • Indexer（本地缓存）：一个带索引的本地内存存储（底层是线程安全的 ThreadSafeStore）。Informer 消费 DeltaFIFO 时，会用最新对象更新 Indexer，因此控制器读取 Get/List 时直接命中它，无需访问 API Server。Indexer 还支持按标签、命名空间等自定义索引快速检索。
  • sharedProcessor / Listener：Informer 消费 DeltaFIFO 时，除了更新 Indexer，还会把事件分发给所有注册的监听器，最终触发用户注册的 AddFunc、UpdateFunc、DeleteFunc。
  • WorkQueue（工作队列）：回调函数通常不直接处理业务逻辑，而是把变化对象的 key 放入一个限速工作队列，再由控制器的 worker 协程从队列中取出、执行真正的调谐（Reconcile）。这样做的好处是：解耦事件接收与业务处理、支持去重与失败重试、削峰限速。

它们串起来的完整链路如下：

graph TB
    A[API Server] -->|List 全量 + Watch 增量| B[Reflector]
    B -->|封装成 Delta 入队| C[DeltaFIFO 队列]
    C -->|消费| D[Informer 主循环]
    D -->|更新对象| E[Indexer 本地缓存]
    D -->|分发事件| F[sharedProcessor 监听器]
    F --> G[AddFunc/UpdateFunc/DeleteFunc]
    G -->|放入对象 key| H[WorkQueue 限速队列]
    H --> I[控制器 Worker 调谐 Reconcile]
    I -->|读取缓存| E

（二）SharedInformer 与 SharedInformerFactory

如果每个控制器都各自创建一个 Informer，就意味着对同一种资源（比如 Pod）维护了多份 List-Watch 连接和多份缓存，既浪费内存又给 API Server 带来重复压力。

SharedInformer 解决的正是这个问题：对同一种资源，只维护一份 Reflector、一份 DeltaFIFO、一份 Indexer 缓存，而允许多个使用者各自注册回调，共享底层的这一套数据。

在实际开发中，一般不直接创建单个 SharedInformer，而是通过 SharedInformerFactory 统一管理。它按资源类型缓存并复用 Informer，同一种资源多次获取拿到的是同一个实例。典型用法是：从 Factory 拿到各资源的 Informer 并注册回调，最后统一 Start 启动、WaitForCacheSync 等待首次全量同步完成后再开始工作，避免缓存尚未就绪就处理业务。

（三）关于 Resync 的准确理解

Resync 是一个容易被误解的概念。它并不是重新去 API Server 拉取数据，而是把 Informer 本地缓存（Indexer）中已有的对象重新投递一遍，触发一次 UpdateFunc（此时新旧对象相同）。

它的意义在于：给控制器一个「定期兜底」的机会，重新对齐期望状态与实际状态，防止某次事件处理失败或遗漏后系统一直处于不一致状态。真正从 API Server 重新拉取全量是 Reflector 在 Watch 连接断开或过期时做的 re-List，二者不是一回事。

四、小结

  • List-Watch 是 Kubernetes 各组件（kubelet、scheduler、controller-manager）感知集群状态的基础机制：先 List 拿全量，再 Watch 收增量。
  • client-go 封装了与 API Server 通信的细节，其中 reflector 是发起 List-Watch 的核心组件。
  • List 是一次性全量快照，Watch 是长连接增量事件流，二者配合借助 resourceVersion 实现实时且一致的状态同步。
  • Informer 在 List-Watch 之上封装了本地缓存与事件回调，减少 API Server 压力，是控制器「事件驱动」高效落地的关键。
