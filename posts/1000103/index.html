Linux 控制组（Cgroups）

在本小节，我们将了解容器的底层原理之一——Cgroup，通过动手实践了解它的作用。

背景

  • cgroup和namespace类似，也是将进程进行分组，但它的目的和namespace不一样，namespace是为了隔离进程组之间的资源，而cgroup是为了对一组进程进行统一的资源监控和限制。
  • cgroup分v1和v2两个版本，v1实现较早，功能比较多，但是由于它里面的功能都是零零散散的实现的，所以规划的不是很好，导致了一些使用和维护上的不便，v2的出现就是为了解决v1中这方面的问题。
  • cgroup v2 是 Linux 内核对 cgroup v1 的重构版本，核心改进是取消子系统拆分、采用统一目录结构，所有资源管控逻辑集中在 /sys/fs/cgroup 根目录下，配置更简洁、避免资源冲突，同时支持更精细的资源控制（如内存压力反馈、CPU 权重动态调整）。

cgroup简介

什么是cgroup

cgroup 是 “control group” 的缩写，并且首字母永远不大写。cgroup 是一种以 hierarchical (树形层级)方式组织进程的机制，以及在层级中以受控和可配置的方式分发系统资源。

  • 单数形式（cgroup）指这个特性，或用户 “cgroup controllers” 等术语中的修饰词
  • 复数形式（cgroups） 显式地指多个cgroup

cgroup 是 Linux 内核的一个功能，用来限制、控制与分离一个进程组的资源（如CPU、内存、磁盘输入输出等）。它最早由Google的工程师（主要是Paul Menage和Rohit Seth）在2006年发起，最早名称为进程容器（process containers）。在2007年时，因为在Linux内核中，容器（container）这个名词有许多不同的意义，为避免混乱，被重新命名为cgroup，并且被合并到2.6.24版的内核中去。

cgroups的一个设计目标是为不同的应用情况提供统一的接口，从控制单一进程（像nice）到作业系统层虚拟化（像OpenVZ，Linux-VServer，LXC）。cgroups 提供：

  • 资源限制：组可以被设置不超过设定的内存限制，包括虚拟内存。
  • 优先级：一些组可能会得到大量的CPU或磁盘IO吞吐量。
  • 结算：用来度量系统实际用了多少资源。
  • 控制：冻结组或检查点和重启动。

cgroup 主要由两部分组成：

  1. 核心（core）：主要负责层级化地组织进程；
  2. 控制器（controllers）：大部分控制器负责cgroup层级中特定类型的系统资源分配，少部分utility控制器用于其他目的。

cgroup v1 v2 对比

cgroup v1 支持多个 hierarchy，每个hierarchy可以启用任意数量的controller。这种方式看上去高度灵活，但实际中并不是很有用。

因此最终的结果就是：

  1. 用户空间最后管理着多个非常类似的 hierarchy，
  2. 在执行 hierarchy 管理操作时，每个 hierarchy 上都重复着相同的操作。

v2 中对 cgroups 的最大更改是将重点放在简化层次结构上

  • v1 为每个控制器使用独立的树（例如 /sys/fs/cgroup/cpu/GROUPNAME 和 /sys/fs/cgroup/memory/GROUPNAME）。

  • v2 将统一/sys/fs/cgroup/GROUPNAME中的树，如果进程 X 加入/sys/fs/cgroup/test，则启用 test 的每个控制器都将控制进程 X。

    对比维度 cgroup v1 cgroup v2
    目录结构 按资源拆分（/cpu、/memory 等） 统一层级（仅 /sys/fs/cgroup 根目录）
    权限控制 默认开启所有资源管控 需通过 cgroup.subtree_control 显式开启
    配置文件 按资源分散（cpu.cfs_quota_us、memory.limit_in_bytes） 集中在同一目录（cpu.max、memory.max）
    资源冲突风险 高（子系统层级独立） 低（统一层级，规则绑定）
    容器工具支持 旧版本默认（如 Docker < 20.10） 新版本默认（如 Docker ≥ 20.10、K8s ≥ 1.25）
    新特性支持 无（如内存软限制、动态权重） 支持（memory.high、cpu.weight 等）

更多 v1 和 v2 差异见 v1 存在的问题及 v2 的设计考虑

cgroup v2 详解

  • cgroup v1 按资源类型拆分 /sys/fs/cgroup/cpu、/sys/fs/cgroup/memory 等子目录，而 cgroup v2 只有一个根目录 /sys/fs/cgroup，所有资源的配置文件（如 CPU、内存、IO）都在同一个控制组目录中，无需跨目录管理。
  • 在启用 cgroup v2 的系统中，/sys/fs/cgroup 下默认包含基础配置文件，创建控制组（子目录）后，内核会自动生成对应资源的配置文件。

输出 cpuset cpu io memory hugetlb pids rdma 对应含义：

资源类型（控制器） 作用说明
cpuset 控制进程可使用的 CPU 核心、NUMA 内存节点（如“只允许用 CPU0 和 CPU1”）
cpu 管控 CPU 使用率（如“限制 50% 核心占用”）、CPU 权重（多进程竞争时的优先级）
io 限制进程的磁盘 I/O 速率（如“读/写速度不超过 100MB/s”）
memory 管控内存使用（如“最大内存 1GB”“禁止用交换分区”）
hugetlb 管控大页内存（HugePage）的使用（针对需要大量内存的数据库、虚拟化场景）
pids 限制控制组内最多可创建的进程数（如“最多允许 100 个进程”）
rdma 管控 RDMA（远程直接内存访问）资源（针对高性能计算、分布式存储场景）

删除 cgroup 组

在 cgroup v2 中，无法直接用 rm -rf 删除控制组目录，核心原因是：控制组目录下的文件（如 cgroup.procs、memory.max）是内核动态生成的“虚拟文件”，并非真实磁盘文件，且删除控制组有严格的内核规则——必须先满足“无进程在组内+无子控制组”两个前提，再用 rmdir（而非 rm -rf）删除。

1. 先清空控制组内的所有进程（关键！）

cgroup 目录下的 cgroup.procs 文件记录了所有关联的进程 PID，必须先将这些 PID 移到其他 cgroup（如根控制组），或直接终止进程。

  • 若进程无法移动（提示“Operation not permitted”），直接用 sudo kill -9 <PID> 终止进程即可。

2. 删除目标 cgroup 的所有子控制组（若有）

如果 host-only-test-cgroup 下还有子目录（子控制组），必须先删除所有子目录，再删除父目录（cgroup 不允许“非空目录”删除）。

3. 用 rmdir 删除目标 cgroup 目录（只能用 rmdir！）

cgroup 目录是“空目录”（无进程、无子组）后，必须用 rmdir（删除空目录的命令）删除，不能用 rm -rf（会试图删除内核虚拟文件，导致权限错误）。

执行后，目标 cgroup 目录会被正常删除，不会再提示“Operation not permitted”。

为什么 rm -rf 不行？

  • cgroup v2 的目录和文件是内核通过“虚拟文件系统”生成的，并非真实磁盘文件：rm -rf 会遍历目录下的所有文件（如 cgroup.procs、memory.max）并试图删除，但这些虚拟文件是内核维护的“只读/只写接口”，内核不允许直接删除这些文件，因此会提示“权限不足”。
  • rmdir 是专门删除“空目录”的命令，只会向内核发送“删除控制组”的请求，内核会先检查“是否满足删除条件”（无进程、无子组），满足则直接回收该 cgroup 的资源，而非删除文件。

总结：cgroup 目录删除的核心规则

  1. 先清进程：确保 cgroup.procs 为空；
  2. 再删子组：确保无任何子控制组；
  3. 用 rmdir：只能用 rmdir 删除空目录，禁用 rm -rf。

Cgroup原理部分

cgroup v2 层级化资源管理

Top-down Constraint（自顶向下约束）

“Top-down（自顶向下）”是 cgroup v2 资源管理的核心逻辑，核心含义是：子 cgroup 的资源控制能力（即“控制器”的启用）完全依赖父 cgroup，父 cgroup 未开放的资源权限，子 cgroup 无法自主启用。

需要先明确一个关键概念：控制器（Controller）
指 cgroup 中用于管理某类资源的功能模块（如 cpu 控制器管 CPU 资源、memory 控制器管内存资源），子 cgroup 要使用某类资源的控制功能，必须先让父 cgroup 把对应的控制器“下放”给自己。

规则1：子 cgroup 只能启用父 cgroup 已开放的控制器

cgroup 中通过 cgroup.subtree_control 文件控制“是否将某个控制器下放给子 cgroup”——父 cgroup 的该文件中包含哪些控制器，子 cgroup 的 cgroup.subtree_control 最多只能包含同样的控制器，不能多出来。

举个例子：

  • 父 cgroup（如 /sys/fs/cgroup/user.slice）的 cgroup.subtree_control 中只有 cpu memory（表示父级只下放了 CPU 和内存控制器）；
  • 它的子 cgroup（如 /sys/fs/cgroup/user.slice/session-c3.scope）的 cgroup.subtree_control 只能包含 cpu、memory 或两者都有，绝对不能出现 io 或 pids 这类父级没下放的控制器。

为什么要这样？
本质是“权限收口”——父 cgroup 先划定自己能管理的资源范围，子 cgroup 只能在这个范围内进一步细分资源，避免子 cgroup 擅自使用父级未授权的资源控制能力，导致整个 cgroup 层级的资源管理混乱。

规则2：父 cgroup 无法禁用“子 cgroup仍在使用”的控制器

当父 cgroup 把某个控制器（如 cpu）下放给子 cgroup 后，只要有任何一个子 cgroup 正在使用该控制器（比如子 cgroup 配置了 cpu.max、或有进程在该控制器下运行），父 cgroup 就不能从自己的 cgroup.subtree_control 中删除这个控制器（即无法“收回”权限）。

举个例子：

  • 父 cgroup 下放了 cpu 控制器给子 cgroup A，子 cgroup A 已配置 cpu.max=2000 10000（正在用 CPU 控制功能）；
  • 此时父 cgroup 执行 echo -cpu > cgroup.subtree_control（试图收回 CPU 控制器）会失败，内核会返回“资源忙”错误。

为什么要这样？
防止父级“强制收回权限”导致子 cgroup 的资源控制失效——如果子 cgroup 正在依赖某个控制器限制资源（如用 cpu.max 控制进程 CPU 占用），父级突然禁用该控制器，会导致子 cgroup 的限制规则失效，进程可能瞬间占用过量资源，引发系统不稳定。

No Internal Process（无内部进程）

这条规则针对“非根 cgroup（non-root cgroup）”，核心含义是：只有当一个非根 cgroup 中没有任何进程（即 cgroup.procs 文件为空）时，它才能将自己的“域控制器（Domain Controller）”下放给子 cgroup；如果该 cgroup 有进程，就不能再向下分发资源控制权限。

先拆解关键概念：

  • 非根 cgroup（non-root cgroup）：除了 /sys/fs/cgroup（根 cgroup）之外的所有 cgroup（如 user.slice、session-c3.scope）；
  • 域控制器（Domain Controller）：指用于“向下分发资源”的控制器（区别于“仅自身使用”的控制器），当一个 cgroup 要把控制器下放给子 cgroup 时，这个控制器对它而言就是“域控制器”，需要写在 cgroup.subtree_control 中。
规则核心：“有进程的 cgroup 不能当‘资源分发者’”

简单说：一个非根 cgroup 只能二选一——要么自己“装进程”（管理进程的资源使用），要么当“资源分发者”（把控制器下放给子 cgroup，让子 cgroup 管理进程），不能两者都做。

举个例子：

  1. 若 cgroup A（非根）的 cgroup.procs 文件中有进程 PID（比如 3796），此时它的 cgroup.subtree_control 无法添加任何控制器（比如想加 cpu 给子 cgroup B，执行 echo +cpu > cgroup.subtree_control 会失败）；
  2. 只有先把 cgroup A 中的所有进程移走（cgroup.procs 为空），才能修改 cgroup.subtree_control，将 cpu 等控制器下放给子 cgroup B；
  3. 子 cgroup B 拿到控制器后，就可以在自己的 cgroup.procs 中添加进程，用父级下放的控制器管理进程资源。
为什么要这样？避免“父子进程资源竞争”

这条规则的核心目的是让 cgroup 层级形成“清晰的分工”：

  • 叶子节点 cgroup：只有叶子节点（层级最末端、没有子 cgroup 的 cgroup）才能有进程，负责直接管理进程的资源使用；
  • 非叶子节点 cgroup：只能做“资源分发者”，负责把父级下放的控制器进一步分给子 cgroup，自己不装进程。

这样能彻底避免“父 cgroup 内的进程与子 cgroup 内的进程竞争资源”的问题——比如若父 cgroup A 自己有进程，又给子 cgroup B 下放了 CPU 控制器，父进程和子进程会同时竞争父 cgroup A 的 CPU 资源，导致资源分配逻辑混乱；而规则强制“非叶子节点无进程”，所有进程都在叶子节点，资源分配只需在“父→子”的分发链路中处理，控制器扫描资源使用时更高效、无冲突。

例外：根 cgroup（root）不受此限制

根 cgroup（/sys/fs/cgroup）可以同时满足两个条件：

  1. 自己的 cgroup.procs 中可以有进程（比如系统初始化时的一些基础进程，或未被分配到其他 cgroup 的“无归属”进程）；
  2. 可以自由修改 cgroup.subtree_control，将控制器下放给子 cgroup（如 user.slice）。

这是因为根 cgroup 是整个 cgroup 层级的“起点”，需要承担“初始化资源分发”和“兜底管理无归属进程”的双重责任，所以内核对其放宽了限制。

cgroup 资源分配模型

cgroup（Control Groups）作为 Linux 内核的资源管理机制，通过四种核心资源分配模型实现对 CPU、内存、IO 等系统资源的精细化管控。各模型基于不同的资源调度逻辑，适用于差异化的资源管理场景，其核心特征、调度机制及适用范围如下：

1. Weights（权重分配模型）

权重模型是一种比例化动态资源调度机制，通过为子 cgroup 配置权重值（weight），在父 cgroup 范围内，仅对“活跃子 cgroup”（即存在资源需求的子 cgroup）按权重比例分配资源，闲置资源自动向需求方转移，实现资源的“工作守恒”（work-conserving）。

  • 活跃性判定：仅当子 cgroup 存在未满足的资源需求（如 CPU 就绪队列非空、IO 请求待处理）时，才被判定为“活跃”，参与权重比例计算；非活跃子 cgroup 不占用资源分配额度。
  • 比例计算逻辑：设父 cgroup 下所有活跃子 cgroup 的权重总和为 ( \sum W_i )，第 ( i ) 个子 cgroup 的权重为 ( W_i )，则其资源分配占比为 ( r_i = W_i / \sum W_i )，父 cgroup 的总可用资源按该比例分配至各活跃子 cgroup。
  • 权重范围：通常取值为 [1, 10000]，默认值 100，支持细粒度的权重调整（如通过 100:200 的权重比实现 1:2 的资源分配）。

适用于无状态、资源需求动态变化的资源类型（如 CPU 时间片、网络带宽），典型场景包括多租户应用的 CPU 共享、非实时服务的资源动态调度，核心目标是最大化资源利用率。

CPU 控制器的 cpu.weight（cgroup v2）或 cpu.shares（cgroup v1），通过权重比例在活跃进程间分配 CPU 周期，避免资源闲置。

2. Limits（限制分配模型）

限制模型是一种静态资源上限约束机制，通过为子 cgroup 配置资源使用的“硬上限”（limit），限定子 cgroup 可消耗的最大资源量；允许“资源超分”（over-commitment），即所有子 cgroup 的限制值总和可大于父 cgroup 的总可用资源，配置合法性不受资源总量约束。

  • 上限约束逻辑：子 cgroup 对目标资源的实际消耗不得超过配置的限制值，一旦达到上限，资源请求将被阻塞或限流（如 IO 请求排队、CPU 调度延迟）。
  • 超分特性：父 cgroup 不校验所有子 cgroup 限制值的总和与自身总资源的匹配关系，仅通过运行时调度确保单个子 cgroup 不超上限；当多子 cgroup 同时触达上限时，父 cgroup 按默认策略（如 FIFO、权重）调度剩余资源。
  • 限制范围：取值为 [0, Max]，其中 0 表示“禁止使用资源”，Max 表示“无限制”（默认值），支持按资源类型的最小粒度配置（如 IO 按 BPS/IOPS 限制、内存按字节限制）。

适用于需控制单个子 cgroup 资源占用峰值的场景（如限制非核心应用的 IO 带宽、避免单个进程耗尽内存），核心目标是防止资源滥用，保障系统整体稳定性。

IO 控制器的 io.max（限制 IO 设备的最大 BPS/IOPS）、内存控制器的 memory.max（限制内存使用上限）。

3. Protections（保护分配模型）

保护模型是一种层级化资源保障机制，通过为子 cgroup 配置“资源保护阈值”（protection threshold），在父 cgroup 及所有祖先 cgroup 均未突破自身保护阈值的前提下，确保子 cgroup 获得不低于阈值的资源量；支持资源超分，保护阈值总和可大于父 cgroup 总资源，保障力度为“最佳努力”（best-effort）。

  • 层级保护逻辑：资源保护具有“自上而下”的层级依赖性——仅当子 cgroup 的所有祖先 cgroup 的实际资源消耗均低于其自身的保护阈值时，子 cgroup 的保护阈值才生效，系统优先满足其子 cgroup 的资源需求（如内存回收时优先回收未达保护阈值的进程）。
  • 超分处理：当所有子 cgroup 的保护阈值总和超过父 cgroup 总资源时，父 cgroup 按保护阈值比例在子 cgroup 间分配可保护资源，即子 cgroup 实际获得的保护资源为“自身阈值 ×（父可用资源 / 子阈值总和）”。
  • 保护范围：取值为 [0, Max]，默认值 0（无保护），支持按资源类型配置（如内存保护、CPU 带宽保护）。

适用于需优先保障关键业务资源需求的场景（如数据库的内存保护、核心服务的 CPU 带宽保障），核心目标是在资源紧张时，优先确保关键子 cgroup 的资源供给。

内存控制器的 memory.low（cgroup v2），确保子 cgroup 在内存回收时，优先保留不低于 memory.low 的内存量；CPU 控制器的 cpu.min（cgroup v2），保障子 cgroup 获得最低 CPU 带宽。

4. Allocations（专属分配模型）

专属分配模型是一种静态资源独占机制，通过为子 cgroup 配置“专属资源额度”（allocation），实现资源的排他性占用；严格禁止“资源超分”，即所有子 cgroup 的专属额度总和不得超过父 cgroup 的总可用资源，否则配置无效（内核拒绝执行）。

  • 独占性约束：子 cgroup 配置的专属资源额度为“排他性预留资源”，仅该子 cgroup 可使用，父 cgroup 及其他子 cgroup 不得占用；若子 cgroup 未用完专属额度，闲置部分也无法被其他子 cgroup 利用（非 work-conserving）。
  • 超分校验：父 cgroup 在接收子 cgroup 的专属额度配置时，会实时校验“已分配额度 + 新配置额度”是否超过自身总可用资源，若超过则返回错误（如 EBUSY），拒绝配置生效。
  • 分配范围：取值为 [0, Max]，默认值 0（无专属资源），仅支持对“可量化、可独占”的资源类型配置（如实时 CPU 时间片、硬件设备配额）。

适用于实时任务（RT）或硬件绑定型应用（如工业控制、音频/视频实时处理、硬件加速卡调度），核心目标是通过资源独占保障任务的确定性执行（如实时任务的 deadlines 满足）。

CPU 实时控制器的 cpu.rt.max（cgroup v2），为子 cgroup 分配专属的实时 CPU 时间片（如 50ms/100ms 周期），确保实时任务不被非实时任务抢占；IO 控制器的 io.allocation（部分内核版本支持），为子 cgroup 分配专属的存储设备 IO 配额。

进程/线程与 cgroup 关系

所有cgroup组成一个树形结构。

  • 系统中的每个进程都属于且只属于某一个cgroup；
  • 一个进程的所有线程属于同一个cgroup；
  • 创建子进程时，继承其父进程的cgroup；
  • 一个进程可以迁移到其他cgroup；
  • 迁移一个进程时，子进程（后台进程）不会自动跟着一起迁移；
