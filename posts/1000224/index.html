Kubernetes 批处理新范式：Kueue 深度解析与实践

发表于2026-08-07|Kubernetes
|总字数:4.8k|阅读时长:17分钟|浏览量:

随着机器学习训练与高性能计算（HPC）向云端迁移，Kubernetes 逐渐从微服务调度扩展到批处理领域。Kueue 应运而生，成为专为 Kubernetes 设计的作业队列管理系统，聚焦资源配额管理、作业优先级调度与异构资源编排。本文整合 Kueue 的架构定位、核心资源对象、高级调度策略与生产实践，帮助你系统性地理解它。

提示：本文示例统一采用稳定版 API kueue.x-k8s.io/v1beta1。早期文档中出现的 v1alpha2 已废弃，字段结构也有差异（如 ResourceFlavor 的污点从顶层 taints 规范到了 spec.nodeTaints），请以本文为准。

一、背景与演进：Kubernetes 的批处理进化之路

随着机器学习训练需求和高性能计算向云端的迁移，Kubernetes 逐渐从微服务调度扩展到批处理领域。2022 年 Google Cloud Next 大会展示的案例（PGS 使用 120 万 vCPU 构建云端超算）标志着这一趋势的加速。传统批处理框架如 Slurm / Mesos 虽在特定场景表现优异，但缺乏 Kubernetes 生态的动态扩展能力和社区支持。

为此，Kubernetes 社区成立批处理工作组（Batch Working Group），推动 Job API 增强和专用组件的研发。Kueue 由此诞生，成为专为 Kubernetes 设计的作业队列管理系统，聚焦资源配额管理、作业优先级调度和异构资源编排。

二、架构定位：作业调度协调者的三重角色

Kueue 定位于 Kubernetes 生态的 作业队列控制器，在不替代 kube-scheduler 和 Job 控制器的基础上，增强三大能力：

  1. 资源仲裁者：通过多级队列控制资源分配
  2. 成本优化器：动态调度作业至最优资源类型（如 Spot 实例）
  3. 生态连接器：与 Cluster Autoscaler 深度集成，支持 Kubeflow / Ray 等框架

它与 Kubernetes 原生组件的关系如下：

简单来说：kube-scheduler 负责把 Pod 放到哪个节点，Kueue 负责决定作业什么时候被允许运行以及占用哪份配额。 两者职责互补，Kueue 处理的是「排队与准入」，调度器处理的是「落点」。

三、核心资源对象

Kueue 通过四个核心对象构建分层资源模型，它们的层级关系是：

3.1 ResourceFlavor：资源类型的抽象定义

ResourceFlavor 描述集群中可用的异构资源类型，通过标签 / 污点机制与物理节点建立映射关系，相当于为集群资源打上分类标签。

它的核心功能包括：

  • 节点选择：通过 nodeLabels 关联特定节点
  • 访问控制：通过 nodeTaints 限制资源使用权限
  • 自动注入：将定义的 tolerations 自动注入到匹配的工作负载

其工作原理为：当工作负载使用带有 ResourceFlavor 的 ClusterQueue 时，Kueue 会比较工作负载的节点亲和性与 ResourceFlavor 的约束，不匹配的会被拒绝调度，匹配的会自动获得 ResourceFlavor 中定义的容忍度。

版本注意：节点标签匹配需要 Kubernetes 1.23+；污点容忍自动注入要求启用 MutatingWebhook；v1beta1 API 需配合 Kueue 0.6.0+ 使用。

3.2 ClusterQueue：集群级资源池

ClusterQueue 是 Kueue 的核心资源池概念，定义了跨命名空间的全局资源配额池，支持多级资源借用策略。它包含三部分：可用资源类型（通过 ResourceFlavor）、资源配额分配规则、资源竞争与调度策略。

配额字段含义：

字段 说明
nominalQuota 基准配额，保障性资源量
borrowingLimit 可借用其他队列的资源上限
lendingLimit 可借出给其他队列的资源量

队列策略对比：

策略类型 调度特点 适用场景
StrictFIFO 严格顺序执行，可能产生队头阻塞 作业依赖性强，需顺序执行
BestEffortFIFO 跳过不可调度作业，资源利用率高 异构作业混合场景

资源借用规则：

  1. 借用总量 ≤ nominalQuota + borrowingLimit
  2. 仅限同 Cohort 内 ClusterQueue 间借用
  3. 单作业只能借用单一 Flavor 资源
  4. 借入方优先级高于贷出方时可触发抢占

ClusterQueue 必须绑定 ResourceFlavor

在 Kueue 中，ClusterQueue 必须至少绑定一个 ResourceFlavor 才能正常工作，不能完全独立使用。这是因为 ClusterQueue 的核心功能是管理资源配额，而配额必须关联到具体的资源类型：集群中可能存在多种资源（CPU、GPU、高内存节点等），需要明确分配哪一种；不同 ResourceFlavor 的配额也是分开管理的。

3.3 LocalQueue：命名空间级接入点

LocalQueue 是 ClusterQueue 在命名空间维度的映射，它把 ClusterQueue 的能力暴露给特定命名空间，实现多租户隔离，并简化用户操作。

运行特征：单个 LocalQueue 只能绑定一个 ClusterQueue；工作流程是用户在工作负载中指定 LocalQueue，Kueue 通过它找到对应的 ClusterQueue，再按 ClusterQueue 的规则进行资源分配。

3.4 Workload：作业的增强抽象

Workload 是 Kubernetes 原生 Job 的增强抽象，支持多框架集成。当你提交一个带 Kueue 队列注解的 Job（或 Kubeflow TFJob、Ray Job 等）时，Kueue 会为其创建对应的 Workload 对象进行排队与准入管理。

3.5 四者的协同关系

在实际使用中，管理员与用户分工协作：

  1. 资源定义阶段（管理员）：创建 ResourceFlavor 描述资源特性 → 创建 ClusterQueue 并绑定 ResourceFlavor → 在各命名空间创建 LocalQueue 关联 ClusterQueue。

  1. 调度决策阶段（Kueue）：Kueue 沿 LocalQueue → ClusterQueue → ResourceFlavor 的完整链路检查配额，若 ClusterQueue 有足够配额则准入作业、注入对应 ResourceFlavor 的节点选择器与容忍度，交由 kube-scheduler 完成落点；若配额不足则让作业继续排队，必要时触发抢占或扩容。最终调度到的节点必须满足 ResourceFlavor 的约束。

3.6 关键约束关系

理解以下三条约束，能帮助你避免常见的配置错误：

  1. ResourceFlavor 必须性：每个 ClusterQueue 必须至少绑定一个 ResourceFlavor；工作负载最终调度到的节点必须满足该 ResourceFlavor 的约束。
  2. 命名空间隔离：LocalQueue 确保只有特定命名空间的工作负载能使用关联的 ClusterQueue，并通过 ClusterQueue 的 namespaceSelector 做二次验证。
  3. 资源借用规则：借用只能在同一 Cohort 的 ClusterQueue 之间发生，且受 borrowingLimit / lendingLimit 限制。

四、高级调度策略

4.1 多维度抢占机制

当集群或 Cohort 资源不足时，Kueue 通过抢占机制确保高优先级工作负载获得资源。抢占通过 ClusterQueue 的 spec.preemption 字段配置，包含三种策略；若不设置，默认都不开启抢占。

1. reclaimWithinCohort（Cohort 内资源回收）

当队列出现排队工作负载时，此策略决定如何从借用了本队列资源的其他队列回收资源。可选值：

  • Never（默认）：不触发回收
  • LowerPriority：仅当资源被优先级较低的工作负载借用时回收
  • Any：不考虑优先级，直接回收被借用的资源

2. borrowWithinCohort（Cohort 内借用时抢占）

控制当队列需要从 Cohort 借用资源时，是否可通过抢占其他队列的资源来获得。前提：必须同时开启 reclaimWithinCohort 且设为非 Never 值。参数：

  • policy：Never（默认，不允许通过抢占借用）/ LowerPriority（只抢占优先级更低者）
  • maxPriorityThreshold：可被抢占工作负载的最高优先级阈值

3. withinClusterQueue（集群队列内部抢占）

控制是否可在同一 ClusterQueue 内抢占其他工作负载。可选值：

  • Never（默认）：不开启队列内抢占
  • LowerPriority：只抢占优先级低于自身的工作负载
  • LowerOrNewerEqualPriority：可抢占优先级更低者；对于同优先级，只抢占比自身创建时间更晚的工作负载（防止大任务被饿死）

策略组合与执行顺序：三者可组合形成多层保障——先尝试从本队列回收借出的资源（reclaimWithinCohort）→ 仍不足则从 Cohort 其他队列抢占（borrowWithinCohort）→ 最后从本队列其他工作负载抢占（withinClusterQueue）。执行流程为：检查目标作业抢占策略 → 计算可释放资源量 → 按优先级逆序选择牺牲者 → 驱逐 Pod 回收资源 → 重试调度。

六、最佳实践与常见问题

最佳实践：

  • ResourceFlavor 设计：按实际硬件差异定义（如 GPU 型号、CPU 架构），通过 taints / tolerations 实现硬隔离。
  • ClusterQueue 规划：生产环境用 StrictFIFO 保证公平性，开发环境用 BestEffortFIFO 提高利用率；合理设置 borrowingLimit 防止资源饿死。
  • LocalQueue 管理：按团队 / 项目划分 LocalQueue，并结合 RBAC 控制访问权限。

常见问题：

  • 能否绕过 LocalQueue 直接使用 ClusterQueue？ 技术上可以，但会破坏多租户隔离，不建议在生产环境这样做。
  • ResourceFlavor 必须对应实际的节点标签吗？ 是的，nodeLabels 必须与节点上存在的标签匹配，否则无法调度。
  • 如何监控资源借用情况？ 通过 Kueue 的 Metrics 或检查 ClusterQueue 状态中的 flavorUsage 字段。

十、小结

Kueue 通过创新的队列机制和分层资源模型，解决了 Kubernetes 在批处理场景的三个核心挑战：资源公平性、成本效益 和 多租户隔离。它的设计充分体现了 Kubernetes 原生组件的扩展哲学——在不颠覆现有体系（kube-scheduler、Job 控制器）的前提下，通过 API 扩展实现能力增强。

回顾全文，它的核心可以浓缩为四层对象的协作：ResourceFlavor 抽象异构资源、ClusterQueue 定义集群级配额池、LocalQueue 提供命名空间接入点、Workload 承载具体作业并参与排队与抢占。对于正在构建 AI 训练平台或混合批处理系统的团队，Kueue 提供了从资源配额、作业调度到成本优化的较完整方案。
