Kubernetes 存储：Volume、持久卷与配置容器

Kubernetes 支持很多类型的卷，一个 Pod 可以同时使用任意数目的卷。按生命周期可以分成两大类：

  • 临时卷：生命周期与 Pod 相同。Pod 被删除时，卷也随之销毁。
  • 持久卷：生命周期可以比 Pod 更长。Pod 不再存在时，Kubernetes 不会销毁持久卷。

需要注意的是：对于给定 Pod 中的任何类型的卷，在容器重启期间数据都不会丢失——因为卷的生命周期跟着 Pod 走，而不是跟着容器走。

graph TD
    A[Volume 卷] --> B[临时卷]
    A --> C[持久卷]
    B --> B1[emptyDir<br/>Pod 删除即清空]
    C --> C1[hostPath<br/>绑定宿主机目录]
    C --> C2[nfs<br/>网络文件系统]
    C --> C3[PV / PVC<br/>持久卷抽象]

一、Volume

emptyDir

对于定义了 emptyDir 卷的 Pod，在 Pod 被指派到某节点时此卷会被创建。就像其名称所表示的那样，emptyDir 卷最初是空的。

它的行为特点：

  • 当 Pod 因为某些原因被从节点上删除时，emptyDir 卷中的数据也会被永久删除。
  • 容器崩溃并不会导致 Pod 被从节点上移除，因此容器崩溃期间 emptyDir 卷中的数据是安全的。

emptyDir 的一些典型用途：

  • 缓存空间，例如基于磁盘的归并排序。
  • 为耗时较长的计算任务提供检查点，以便任务能方便地从崩溃前状态恢复执行。
  • 在 Web 服务器容器服务数据时，保存内容管理器容器获取的文件。

hostPath

hostPath 卷把 Pod 所在宿主机上的某一目录（脱离 Pod 中容器的名称空间）和 Pod 建立关联关系。Pod 删除时，存储数据不会丢失。

生产环境其实不推荐使用 hostPath，因为它把 Pod 和具体宿主机绑定，既不安全（可访问宿主机文件系统），也破坏了 Pod 的可调度性。

hostPath 的 type 字段相当重要，常用取值：

type 含义
DirectoryOrCreate 目录不存在则创建
Directory 目录必须已存在
FileOrCreate 文件不存在则创建（但不会创建父目录）
File 文件必须已存在

因为 FileOrCreate 模式不会创建文件的父目录，如果挂载文件的父目录不存在，Pod 将启动失败。所以需要分别声明父目录卷和文件卷：

NFS

nfs 卷能将 NFS（网络文件系统）挂载到你的 Pod 中。

不像 emptyDir 那样会在删除 Pod 的同时被删除，nfs 卷的内容在删除 Pod 时会被保留，卷只是被卸载。这意味着 nfs 卷可以被预先填充数据，并且这些数据可以在 Pod 之间共享。

使用前需要提前在节点上安装 NFS 客户端，并配置好 NFS 服务。

CSI

CSI（Container Storage Interface，容器存储接口）是 Kubernetes 对接第三方存储系统的标准化接口。

在 CSI 出现之前，每接入一种存储（NFS、Ceph、云盘等）都要把驱动代码编译进 Kubernetes 主干（称为 in-tree 卷插件），耦合严重、迭代困难。CSI 把存储驱动从 Kubernetes 核心中剥离出来，存储厂商只需按接口规范实现自己的 CSI 驱动（以独立组件形式部署到集群），Kubernetes 就能通过统一接口完成卷的创建、挂载、卸载、删除。

简单说：CSI 让存储插件成为可插拔的外部组件，而不必修改 Kubernetes 本身。 后面要讲的 StorageClass 动态供给，底层依赖的正是 CSI 驱动。

二、持久卷相关

前面的 hostPath、nfs 都要求使用者直接在 Pod 里写清楚存储的具体细节（服务器地址、路径等）。这样做的问题是：使用存储的人（开发）和管理存储的人（运维）被强耦合在了一起。 PV / PVC / SC 这套抽象就是为了解耦它们。

PV、PVC 和 SC

  • PV（PersistentVolume，持久卷）：集群中的一块存储资源，由管理员预先配置或通过动态 provisioner 自动创建，是物理资源的抽象。
  • PVC（PersistentVolumeClaim，持久卷申领）：当我们创建一个 Pod 需要申请一块空间时，这个申请就是 PVC。它声明「我要多大、什么访问模式」，而不关心底层是 NFS 还是云盘。
  • SC（StorageClass，存储类）：为不同的存储后端提供了不同的类别。SC 定义了存储的类型、性能参数、provisioner（存储制备器）等信息，用于动态创建 PV。

一句话概括三者关系：PVC 是需求，PV 是供给，SC 是按需自动生产 PV 的模板。

PV、PVC、SC 的协作流程

  1. 用户提交 PVC：在集群中提交一个 PVC，声明所需的存储特性，如存储大小、访问模式等。
  2. 匹配 StorageClass：
    • 如果 PVC 指定了特定的 StorageClass，则使用该 StorageClass。
    • 如果 PVC 没有指定 StorageClass 而集群有默认的 StorageClass，则使用默认的 StorageClass。
  3. 动态创建 PV：Kubernetes 调用 StorageClass 声明的存储插件（如 nfs.csi.k8s.io）来动态创建一个新的 PV。存储插件本身就是一个个运行在节点上的 Pod（NFS、S3 等各种类型），它根据 StorageClass 的参数（如 server、share）和挂载选项（如 rw、hard）来配置存储资源。
  4. PV 和 PVC 绑定：新创建的 PV 绑定到 PVC，此后 PV 专门为该 PVC 服务，直到 PVC 被删除。
  5. Pod 使用存储：Pod 通过 PVC 访问到绑定的 PV，从而使用存储资源。
  6. 存储回收：当 PVC 被删除时，根据 StorageClass 的回收策略（reclaimPolicy），PV 可以被自动删除（Delete，数据丢失）或者保留（Retain，数据保留）。

三、配置容器：CM 和 Secret

在 Kubernetes 中，用户通过 ConfigMap 和 Secret 从集群外部向 Pod 内部的容器应用注入配置信息，从而让配置与镜像解耦。

Secret

Secret 对象以键值方式存储数据，专门用于存储密码、密钥、证书等敏感信息。

它的几个关键特性：

  • 数据的存储和打印格式为 Base64 编码的字符串，因此用户在创建 Secret 时也需要提供 Base64 编码格式的数据。在容器中以环境变量或存储卷方式访问时，会自动解码为明文。
  • Base64 只是编码、不是加密。在 Master 节点上，Secret 以非加密的格式存储在 etcd 中，所以需要对 etcd 的管理和权限进行严格控制。

Secret 的四种类型：

  • Service Account：用来访问 Kubernetes API，由 Kubernetes 自动创建，并自动挂载到 Pod 的 /run/secrets/kubernetes.io/serviceaccount 目录中。
  • Opaque：Base64 编码格式的通用 Secret，用来存储密码、密钥、证书等，命令式创建的类型标识为 generic。
  • kubernetes.io/dockerconfigjson：用来存储私有 docker registry 的认证信息，类型标识为 docker-registry。
  • kubernetes.io/tls：用于为 SSL 通信存储证书和私钥文件，命令式创建的类型标识为 tls。

ConfigMap

ConfigMap 让配置文件从镜像中解耦，从而提升镜像的可移植性和可复用性。ConfigMap API 提供了向容器中注入配置信息的机制，既可以保存单个属性，也可以保存整个配置文件或者 JSON 二进制大对象。

ConfigMap 和 Secret 非常类似，创建和使用方式几乎一致。核心区别只有一点：Secret 用于敏感数据（Base64 存储），ConfigMap 用于普通配置（明文存储）。 因此这里不再重复展开示例。
