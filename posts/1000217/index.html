Kubernetes 包管理器 Helm 入门：架构、工作流程与 Chart 结构

发表于2026-08-06|Kubernetes
|总字数:1.6k|阅读时长:5分钟|浏览量:

一、Helm 是什么

Helm 是 Kubernetes 的包管理器，就像 Linux 世界里的 apt / yum 一样，能快速查找、下载、安装和管理为 Kubernetes 构建的软件包。它把一组相关的 Kubernetes 资源打包成一个可复用、可版本化的整体来统一管理。

版本说明（重要）：早期的 Helm 2 采用「客户端 helm + 服务端 Tiller」的架构，Tiller 常驻集群、代表用户操作 API Server，带来了权限过大、安全隐患等问题。Helm 3（2019 年底发布，目前的主流版本）已彻底移除 Tiller，改为纯客户端架构：helm 直接使用你本地 kubeconfig 的凭据与 API Server 通信，权限与 RBAC 完全对齐。本文以 Helm 3 为准，下文不再涉及 Tiller。

二、Helm 解决的痛点

在 Kubernetes 中部署一个真正可用的应用，往往需要多个资源协作。以部署一个 WordPress 博客为例：

  • Deployment：部署应用本体。
  • Service：提供服务发现与访问入口。
  • Secret：存放 WordPress 的用户名和密码等敏感配置。
  • PV / PVC：提供持久化存储。
  • 依赖 MariaDB：WordPress 的数据存储在 MariaDB 中，必须等数据库就绪后才能启动。

这些资源分散且相互依赖，直接用 kubectl 逐个管理非常困难。归纳起来主要面临三个问题：

  1. 如何统一管理、配置和更新这些分散的资源文件？
  2. 如何分发和复用一套应用模板？
  3. 如何把应用的一系列资源当成一个软件包来整体管理？

Helm 正是为解决这些问题而生。

三、Helm 核心概念

概念 说明
helm 命令行客户端，用于开发、管理 Chart，操作 Chart 仓库，以及在集群中安装 / 升级 / 卸载应用
Chart Helm 的打包格式，本质是一系列文件，描述一组相关的 Kubernetes 资源
Release 使用 helm install 在集群中部署出来的一个 Chart 实例；同一个 Chart 可以安装出多个 Release
Repository Chart 仓库，Helm 客户端通过 HTTP 协议访问其中的索引文件和 Chart 压缩包
Values 提供给 Chart 模板的配置值，可通过 values.yaml、-f 或 --set 覆盖

四、Helm 工作流程

以一次 helm install / helm upgrade 为例，Helm 内部大致经历以下阶段。

1. 读取 Chart 与合并 Values

  • 读取 Chart：读取指定 Chart 的 Chart.yaml、values.yaml 以及 templates/ 目录下的模板文件。
  • 合并 Values：将 values.yaml 中的默认值与用户通过 --set 或 -f 提供的自定义值合并，形成最终配置。

2. 渲染模板

  • 模板渲染：使用 Go 模板引擎，把 templates/ 下的模板（如 deployment.yaml）渲染成最终的 Kubernetes 资源清单。
  • 替换占位符：模板中的占位符（如 {{ .Values.image.tag }}）被替换为实际值。
  • 生成资源清单：最终得到一份完整的 Kubernetes 资源定义，例如 Deployment、Service 等。

3. 计算差异（升级场景）

  • 渲染新清单：根据新的 Chart 与 Values 渲染出新的资源清单。
  • 获取当前状态：从集群中读取已部署资源的当前状态。
  • 对比差异：Helm 对所有渲染出的资源（Deployment、ConfigMap、Service 等）逐一做声明式对比，哪个对象发生了变更就更新哪个，未变化的保持不动。

常见误区澄清：关于「修改了 ConfigMap 模板后 Helm 是否会更新」，答案是——Helm 能检测到 ConfigMap 的变更并更新 ConfigMap 对象本身（它对所有资源做声明式对比，ConfigMap 并不例外）。真正的坑在于：引用该 ConfigMap 的 Pod 不会因为 ConfigMap 内容变化而自动重启，因此新配置可能不会立即生效。业界通用做法是在 Deployment 的 Pod 模板注解里加一个 ConfigMap 内容的 checksum：

4. 执行更新

  • 应用资源清单：Helm 将渲染后的清单提交给 Kubernetes API Server，请求创建 / 更新资源。
  • Kubernetes 处理更新：API Server 按资源类型执行相应操作。对于 Deployment，可能包括创建新 Pod 副本、逐步替换旧副本等（滚动更新）。

五、Chart 结构详解

Chart 说白了就是一系列文件，经过组织和渲染后得到若干 Kubernetes 资源模板（如 Deployment、Secret、ConfigMap 等），再统一部署到集群，从而达到「一次更新多个组件」的效果。

各部分的作用：

  • Chart.yaml：Chart 包的元信息（名称、版本、描述等）。
  • values.yaml：存放模板中用到的各种默认「值」。由于 Chart 包常常是自动打包的，某些默认值可能与期望不符，因此这些值可以在安装 / 升级时通过 -f 或 --set 覆盖。
  • templates/：模板目录，存放应用一系列 Kubernetes 资源的 YAML 模板，是渲染出最终清单的核心。可按业务需求添加各种模板，其中最常用的是 deployment.yaml。
    • configmap.yaml：用于动态生成 ConfigMap 资源，通常会引用 files/ 和模板中的文件，也可能包含数据库初始化脚本。
    • deployment.yaml：更新应用工作负载时使用的模板，一般由 Deployment（或 DaemonSet）渲染而来。
    • _helpers.tpl：定义可复用的模板片段，其中的定义在任意资源模板中都可引用。
    • sql/：数据库初始化相关的 SQL 内容。
  • files/：一般存放静态文件，供模板引用。

六、小结

  • Helm 是 Kubernetes 的包管理器，把一组相关资源打包成 Chart，安装后成为一个 Release，通过 Repository 分发。
  • Helm 3 已移除 Tiller，纯客户端架构直连 API Server，权限与 RBAC 对齐，比 Helm 2 更安全。
  • 工作流程可概括为：读取 Chart → 合并 Values → Go 模板渲染 → 声明式对比差异 → 提交 API Server 更新。
  • ConfigMap 变更 Helm 能检测并更新，但 Pod 不会自动重启；用 checksum 注解触发滚动更新是标准解法。
  • Chart 目录以 Chart.yaml（元信息）、values.yaml（默认值）、templates/（资源模板）为核心。
