Kubernetes 容器运行时详解：从原理、CRI 到运行时选型

发表于2026-08-06|Kubernetes
|总字数:2.6k|阅读时长:8分钟|浏览量:

一、什么是容器运行时

容器运行时（Container Runtime）提供容器的运行环境，是负责运行容器的软件。通俗地讲，它管理容器从拉取镜像、创建、启动、运行、销毁的完整生命周期。

以 Docker 为例，作为一个整体的容器运行时实现，主要提供：

  • 制定容器镜像格式
  • 构建容器镜像
  • 运行容器

二、容器运行时的分类

1. 高层运行时与低层运行时

目前较流行的说法按功能实现把容器运行时分为两类：

  • 低层运行时（low-level）：通常只关注 Namespace、Cgroups、镜像拆包等基础的容器运行实现（如 runc）。
  • 高层运行时（high-level）：支持更多高级功能（如镜像管理、CRI 实现）的运行时（如 containerd、CRI-O）。

2. 按隔离技术分类

（1）基于 hypervisor 的运行时

  • 代表技术：KVM、Kata Containers 等。
  • 原理：利用 hypervisor 在物理主机上创建多个虚拟机，每个虚拟机有独立的操作系统和资源隔离环境，容器运行在虚拟机内部，实现更强隔离。
  • 优点：硬件级强隔离，安全性高，一个容器的故障或攻击很难影响其他容器或主机；可灵活分配 CPU / 内存 / 存储等资源。
  • 缺点：需模拟完整硬件环境并运行独立操作系统，启动较慢、资源占用较大、性能开销较高。

（2）基于 Linux 容器的运行时

  • 代表技术：Docker、runc、containerd 等。
  • 原理：利用 Linux 内核的命名空间（Namespace）、控制组（Cgroup）实现隔离与资源限制。Namespace 隔离进程、网络、文件系统等资源，Cgroup 限制 CPU、内存等使用量。
  • 优点：启动快（无需加载完整操作系统）；资源利用率高（多容器共享主机内核）；镜像体积小，便于部署分发。
  • 缺点：隔离性相对较弱，某些情况下（如内核漏洞利用）可能突破容器隔离；对特殊硬件的支持不如虚拟机完善。

（3）基于其他技术的运行时

  • 代表技术：Wasm（WebAssembly）运行时等。
  • 原理：Wasm 是一种字节码格式，提供安全、轻量的执行环境。基于 Wasm 的运行时把应用编译为 Wasm 字节码，在 Wasm 运行时中执行。
  • 优点：安全性极高（沙盒机制防止未授权访问）；启动极快；可移植性强，字节码可跨平台运行。
  • 缺点：生态相对较小，对复杂应用场景和部分系统调用的支持还不够完善。

三、安全容器运行时 Kata

尽管容器有诸多优势，但传统以 runc 为代表、基于共享内核的软隔离仍存在风险：若恶意程序利用系统缺陷从容器逃逸，会对宿主机造成严重威胁——尤其在公有云环境，可能波及其他用户的数据和业务。

Kata Containers 正是为「把虚拟机的安全优势与容器的高速、可管理性结合」而生，为用户提供标准化、安全、高性能的容器方案。它解决了普通容器难以应对的多租户安全、不同 SLO 混部、可信 / 不可信容器混部等问题，同时在虚拟化上追求极致轻薄，让资源消耗和弹性接近 runc 方案，达成 Secure as VM、Fast as Container 的目标。

Kata Containers 的特点：

  • 容器与虚拟机二合一：兼具容器的高性能、高效管理与虚拟机的独立隔离、安全性。
  • 安全性：用轻量级虚拟化为每个容器创建轻量虚拟机，实现容器级隔离。
  • 可扩展性：可与 Docker、Kubernetes 等容器管理工具集成，无缝接入现有环境。
  • 兼容性：支持 OCI 规范，兼容现有容器镜像和工具。

四、CRI：Kubernetes 的容器运行时接口

1. 为什么需要 CRI

Kubernetes 从 1.5 版本开始，在遵循 OCI 的基础上，将容器操作抽象为一个接口，作为 Kubelet 与运行时实现对接的桥梁。Kubelet 通过发送接口请求来启动和管理容器，各容器运行时只要实现该接口即可接入 Kubernetes。

这个接口就是 CRI（Container Runtime Interface）。

2. CRI 主要组件

CRI 是一套通过 Protocol Buffer 定义的 API，主要有 gRPC Client、gRPC Server 和具体容器运行时实现三个组件：

  • Kubelet 作为 gRPC Client，调用 CRI 接口。
  • CRI shim 作为 gRPC Server，响应 CRI 请求，并负责将 CRI 请求转换为具体运行时的管理操作。

对于 Kubernetes，需要在集群内每个 Node 节点上安装一个容器运行时，Pod 才能运行其上。

3. Protocol Buffers API

CRI 包含两个 gRPC 服务：

  • ImageService：提供从仓库拉取镜像、查看和移除镜像的功能。
  • RuntimeService：负责 Pod 和容器的生命周期管理，以及与容器的交互（exec / attach / port-forward）。

容器运行时可以用一个 Socket 同时提供这两个服务，在 kubelet 中可用 --container-runtime-endpoint 和 --image-service-endpoint 参数设置该 Socket。

4. 创建容器的流程

graph TB
    A[调度器选择节点] --> B[目标节点 Kubelet 接收 Pod 创建请求]
    B --> C[Kubelet 通过 CRI 发起创建请求]
    C --> D[CRI shim 转换为具体运行时指令]
    D --> E[运行时创建 Pod Sandbox]
    E --> F[运行时管理 Sandbox 与容器生命周期]
    F --> G[结果反馈给 Kubelet]
  1. 调度选择节点：调度器根据资源需求和策略选择合适节点运行 Pod。
  2. Kubelet 接收请求：选定节点的 Kubelet 接收 Pod 创建请求，准备启动。
  3. CRI 请求处理：Kubelet 通过 CRI 向运行时发起创建请求，CRI shim 将标准化的 CRI 请求转换为具体运行时指令。
  4. Pod Sandbox 创建：运行时创建 Pod Sandbox，提供共享运行环境，隔离网络和文件系统。Linux 环境下 Sandbox 可能是一个命名空间；Hypervisor 环境下则为虚拟机。
  5. 运行时管理：运行时负责 Pod Sandbox 的生命周期（创建、启动、停止），提供资源隔离和进程管理。
  6. 结果反馈：运行时将处理结果返回给 Kubelet，完成创建流程。

五、常见容器运行时选型

Kubernetes 通过 CRI 与运行时交互，常见的运行时如下。

（1）containerd：轻量级运行时，专注容器核心功能（镜像管理、生命周期管理）。性能高、与 Kubernetes 集成良好、支持 OCI 标准，是推荐运行时之一。不直接提供网络 / 存储等高级功能，需依赖 CNI、CSI 等组件。适用于大多数集群的通用场景。

（2）CRI-O：专为 Kubernetes 设计、完全遵循 CRI 标准。轻量高效、完全开源、支持 OCI。功能相对单一，主要面向 Kubernetes。适用于专注 Kubernetes 的环境。

（3）Docker（作为 K8s 运行时已退场）：Docker 是最早的容器运行时之一，工具链丰富、社区广泛。

准确说明：常被误传为「Docker 被弃用」。准确的说法是——Kubernetes 在 1.20 弃用了 dockershim（Kubelet 内置的 Docker 适配层），并在 1.24 正式移除。这意味着 Kubelet 不再内置支持直接以 Docker 作为运行时，但 Docker 构建的镜像（OCI 镜像）依旧完全可用，可正常运行在 containerd、CRI-O 等运行时上。开发环境仍可继续用 Docker 构建镜像。

（4）Kata Containers：基于虚拟化，为每个容器 / Pod 提供独立虚拟机内核。隔离性和安全性更强，兼容 OCI，可与 containerd 或 CRI-O 集成；但性能开销较大、启动较慢、资源占用较高。适用于高安全 / 隔离场景（多租户、运行不受信任代码）。

（5）gVisor：用户空间内核，为容器提供额外安全隔离。安全性强于传统容器，性能开销低于虚拟机；但兼容性较差（部分系统调用不支持），性能仍低于传统容器。适用于需要较高安全性、但对性能要求不极端的场景。

（6）Firecracker：轻量级虚拟机管理器，专注安全与性能。启动快、资源占用低，提供虚拟机级隔离；需额外集成（如 containerd 的 firecracker-containerd 插件）。适用于轻量级虚拟化场景（如无服务器计算）。

六、默认运行时与查看配置

1. 默认运行时

创建 Pod 时若不配置 runtimeClassName，Kubernetes 使用集群配置的默认运行时。通常：

  • 大多数集群默认运行时是 containerd 或 CRI-O。
  • 具体取决于集群安装 / 配置方式，例如：
    • 使用 kubeadm 安装的集群，默认运行时通常是 containerd。
    • 使用特定发行版（如 OpenShift）的集群，默认运行时可能是 CRI-O。

2. 查看与配置

查看节点的容器运行时：

默认运行时通常在节点的配置文件中指定：

  • containerd：/etc/containerd/config.toml
  • CRI-O：/etc/crio/crio.conf

如需更改，可修改节点配置文件并重启相关服务。

七、小结

  • 容器运行时负责容器的完整生命周期，按功能分为高层 / 低层，按隔离技术分为 hypervisor、Linux 容器、Wasm 等类型。
  • Kata Containers 用轻量虚拟化实现「Secure as VM、Fast as Container」，适合高安全 / 多租户场景。
  • CRI 是 Kubelet 与运行时之间的标准接口，包含 ImageService 与 RuntimeService 两个 gRPC 服务，让任意实现 CRI 的运行时都能接入 Kubernetes。
  • 选型上：通用场景选 containerd，纯 Kubernetes 环境可选 CRI-O，高安全场景考虑 Kata / gVisor / Firecracker；Docker 已不再作为 K8s 运行时，但其镜像仍通用。
