Kubernetes StatefulSet 与 Headless Service

无状态应用可以随意扩缩、随意重建，谁顶上都一样；但数据库、消息队列这类有状态应用不行——每个实例都有自己的身份和数据，重建后必须”还是原来那个”。Kubernetes 用 StatefulSet + Headless Service 这对组合来解决这个问题。本文先讲清 Headless Service，再讲它如何与 StatefulSet 协同。

一、Headless Service 介绍

Headless Service（无头服务）是 Kubernetes 中的一种特殊 Service 类型，它不会为 Service 分配集群 IP（ClusterIP），也不做负载均衡或请求代理。

主要特点

  • 无集群 IP：与常规 Service 不同，Headless Service 没有 ClusterIP 地址。
  • 直接 DNS 解析：DNS 查询会返回所有匹配 Pod 的 IP 地址列表，而不是单个 Service IP。
  • 每个 Pod 有独立 DNS 记录：每个 Pod 会获得一个唯一的、可解析的 DNS 名称。

使用场景

  • 需要直接与特定 Pod 通信，而不是通过代理。
  • 需要知道所有 Pod 的 IP 地址。
  • StatefulSet 需要稳定的网络标识。

二、Headless Service 与 StatefulSet 的联系

Headless Service 与 StatefulSet 是 Kubernetes 中为有状态应用设计的两个紧密相关的概念。

协同工作机制

稳定的网络标识：

  • StatefulSet 为每个 Pod 提供有序的、稳定的标识（如 web-0、web-1、web-2）。
  • Headless Service 为这些 Pod 提供可解析的 DNS 名称（如 web-0.my-headless-service.namespace.svc.cluster.local）。

DNS 记录：

  • 每个 StatefulSet Pod 通过 Headless Service 获得唯一的 DNS 名称。
  • 这些名称在 Pod 重启或重新调度时保持不变。

有序部署和扩展：

  • StatefulSet 保证 Pod 按顺序创建和扩展（0, 1, 2, …）。
  • Headless Service 确保每个 Pod 有稳定的网络标识与之对应。

为什么 StatefulSet 需要 Headless Service

  • 直接 Pod 访问：有状态应用通常需要直接访问特定实例，而不是通过负载均衡器。
  • 稳定的网络拓扑：即使 Pod 重新调度到其他节点，DNS 名称保持不变。
  • Peer 发现：在集群应用中（如数据库），Pod 需要发现并相互通信。

有状态与无状态的差异

使用 Deployment 创建的 Pod 是无状态的，如果某个 Pod 挂了，其背后的 ReplicaSet 会再启动一个 Pod 来保证可用性。但由于 Pod 是无状态的，Pod 挂了就会和之前的 Volume 的关系断开，新创建的 Pod 无法找到之前 Pod 的数据。

StatefulSet 就是为了解决有状态服务的问题而设计的，它提供以下保证：

  • 稳定的持久化存储：Pod 重新调度后仍能访问到相同的持久化数据，基于 PVC 来实现。
  • 稳定的网络标识：Pod 重新调度后其 PodName 和 HostName 不变，基于 Headless Service（即没有 ClusterIP 的 Service）来实现。
  • 有序部署、有序扩展：Pod 是有顺序的，部署或扩展时依据定义的顺序依次进行（从 0 到 N-1，在下一个 Pod 运行之前，所有之前的 Pod 必须都处于 Running 和 Ready 状态），基于 init containers 来实现。
  • 有序收缩、有序删除。
  • 有序的滚动更新。

三、StatefulSet 的三大组成

从上面的应用场景可以发现，一个完整的 StatefulSet 控制器由以下几个部分组成：

  • Headless Service（无头服务）：用于为 Pod 资源标识符生成可解析的 DNS 记录。
  • VolumeClaimTemplates（存储卷申请模板）：基于静态或动态 PV 供给方式，为 Pod 资源提供专有的固定存储。
  • StatefulSet：用于管控 Pod 资源。

Headless Service

在 Deployment 中，每一个 Pod 是没有固定名称的，是随机字符串，是无序的。而 StatefulSet 要求有序，每一个 Pod 的名称必须是固定的：当节点挂了、重建之后，标识符不变，每一个节点的名称不能改变。Pod 名称作为 Pod 识别的唯一标识符，必须保证其稳定并且唯一。

为了实现标识符的稳定，这时候就需要一个 Headless Service 解析直达到 Pod，还需要给 Pod 配置一个唯一的名称。

VolumeClaimTemplate

大部分有状态副本集都会用到持久存储。比如分布式系统，由于数据是不一样的，每个节点都需要自己专用的存储节点。

在 Deployment 的 Pod 模板中创建的存储卷是一个共享的存储卷，多个 Pod 使用同一个存储卷。而 StatefulSet 定义中的每一个 Pod 都不能使用同一个存储卷：volumeClaimTemplates 允许为每个 Pod 自动创建独立的 PersistentVolumeClaim（PVC），从而为每个 Pod 提供独立的持久化存储。

StatefulSet 通过 volumeClaimTemplates 创建的 PVC 是与 Pod 绑定的，即使 Pod 被重新调度到其他节点，它仍然可以访问相同的持久卷。使用 volumeClaimTemplates 可以自动为每个 Pod 创建 PVC，而无需手动为每个 Pod 配置存储。这大大简化了有状态应用的管理，尤其是在 Pod 数量较多时。

六、更新策略

StatefulSet 提供了两种更新策略：RollingUpdate 和 OnDelete。可以在 spec.updateStrategy.type 中指定：

OnDelete 策略

当更新策略设置为 OnDelete 时：

  • StatefulSet 控制器不会自动更新 Pod。
  • 只有在手动删除某个 Pod 后，控制器才会用新模板创建新的 Pod。
  • 这种方式提供了最大程度的控制，但需要手动干预。

RollingUpdate 策略

RollingUpdate 是默认策略：

  • StatefulSet 控制器会自动删除并重建 Pod。
  • 更新是有序进行的（从最高序号到最低序号）。
  • 每次更新一个 Pod，等待它进入 Running 和 Ready 状态后再更新下一个；如果更新过程中某个 Pod 失败，更新会暂停。
  • 支持两个精细控制参数：partition 和 maxUnavailable。

partition 参数

partition 是 RollingUpdate 策略中最重要且独特的参数：

作用：

  • 指定一个序号，只有序号大于或等于此值的 Pod 才会被更新。
  • 序号小于此值的 Pod 将保持不变。

使用场景：

  • 分阶段更新：先更新部分 Pod 进行测试，确认无误后再更新剩余 Pod。例如有 5 个副本，初始设置 partition: 3，则只有 web-3、web-4 会被更新；测试通过后，将 partition 改为 0 更新所有 Pod。
  • 金丝雀发布：先更新少量 Pod 作为金丝雀。将 partition 设置为副本数减一（如 5 个副本设为 4），只更新一个 Pod 进行验证。
  • 回滚机制：如果更新后发现问题，可以增大 partition 值阻止进一步更新。

示例流程：

maxUnavailable 参数

作用：

  • 指定在更新过程中最多可以有多少个 Pod 不可用。
  • 可以设置为绝对值（如 1）或百分比（如 20%），默认值为 1。

行为特点：

  • 控制并行更新的 Pod 数量，确保在更新过程中始终有足够数量的 Pod 提供服务。
  • 与 Deployment 的 maxUnavailable 类似，但实现方式不同。

注意事项：

  • 对于 StatefulSet，maxUnavailable 的实际行为受有序性约束：即使设置大于 1，StatefulSet 仍然会按序号逆序更新，它主要影响的是更新速度，而不是真正的无序并行更新。
  • maxUnavailable 用于 StatefulSet 是较新版本才引入的特性（需要开启对应的特性门控 / 使用支持它的集群版本），在旧版本集群上可能不生效。

实际应用建议

  • 生产环境：使用 RollingUpdate 结合 partition 进行分阶段更新。
  • 关键系统：先更新少量 Pod（设置较高 partition 值）进行验证。
  • 回滚：通过增大 partition 快速停止有问题的更新。
  • 性能敏感型应用：合理设置 maxUnavailable 平衡更新速度和服务可用性。

七、总结

Headless Service 和 StatefulSet 共同为 Kubernetes 中的有状态工作负载提供了稳定的网络标识和发现机制。这种组合特别适合需要以下特性的应用：

  • 稳定的、可预测的 Pod 名称
  • 持久化存储
  • 有序部署和扩展
  • 需要直接 Pod 到 Pod 通信的场景
