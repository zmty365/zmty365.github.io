Kubernetes Pod 基础

一、Pod 是什么

Pod 是 Kubernetes 中最小的可部署和可调度单元。一个 Pod 封装了一个或多个紧密关联的容器，这些容器共享同一份网络命名空间（Network Namespace）和存储卷（Volume），可以通过 localhost 相互通信。

之所以要有 Pod 这一层抽象，而不是直接调度容器，是因为现实中很多应用是”超亲密关系”的容器组合。例如一个主容器加一个负责收集日志的 Sidecar 容器，它们需要共享同一份文件和网络，必须被作为一个整体来调度、部署和扩缩容。

二、Pod 的生命周期与状态

Pod 在其生命周期中会处于不同的阶段（Phase），这个状态记录在 status.phase 字段中。主要状态如下：

状态 含义
Pending Pod 已被 Kubernetes 接受，但还有容器未创建完成（如正在拉取镜像、等待调度）
Running Pod 已绑定到节点，所有容器都已创建，至少有一个容器仍在运行或正在启动/重启
Succeeded Pod 中所有容器都已成功终止，且不会再重启
Failed Pod 中所有容器都已终止，且至少有一个容器是因失败而终止
Unknown 无法获取 Pod 状态，通常是与所在节点通信失败导致

需要注意的是，容器（Container）自身还有独立的状态：Waiting、Running、Terminated，不要与 Pod 的 Phase 混淆。

三、容器探针（Probe）

kubelet 通过探针（Probe）来判断容器的健康状况，从而决定是否重启容器、是否将流量导入容器。Kubernetes 提供三种探针：

  • livenessProbe（存活探针）：判断容器是否存活。探测失败时，kubelet 会杀死容器并按照重启策略处理。用于解决进程假死问题。
  • readinessProbe（就绪探针）：判断容器是否准备好对外提供服务。探测失败时，Endpoint 控制器会将该 Pod 的 IP 从对应的 Service 中摘除，不再向它转发流量。
  • startupProbe（启动探针）：判断容器内应用是否已完成启动。在它成功之前，其他两种探针都会被禁用，用于保护启动较慢的应用不被存活探针提前杀死。

探针支持三种探测方式：exec（在容器内执行命令，返回 0 视为成功）、httpGet（发起 HTTP 请求，状态码 2xx/3xx 视为成功）、tcpSocket（尝试建立 TCP 连接，成功即视为健康）。

四、Init 容器

Init 容器是一种特殊容器，它在 Pod 中的应用容器（主容器）启动之前运行，常用于完成初始化工作，例如等待依赖服务就绪、拉取配置文件、执行数据库迁移等。

Init 容器有两个关键特点：

  • 串行执行：一个 Pod 可以有多个 Init 容器，它们按定义顺序一个接一个地运行，前一个成功退出后才会启动下一个。
  • 必须成功：所有 Init 容器都成功结束后，主容器才会启动。任一 Init 容器失败，kubelet 会按 Pod 的 restartPolicy 反复重启它，直到成功。

由此可以画出一个 Pod 从创建到就绪的完整生命周期：

graph TD
    A[Pod 被调度到节点] --> B[Init 容器 1]
    B --> C[Init 容器 2]
    C --> D{全部 Init 成功?}
    D -- 否 --> B
    D -- 是 --> E[启动主容器]
    E --> F[postStart 钩子]
    F --> G[startupProbe 启动探针]
    G --> H[liveness / readiness 探针持续工作]
    H --> I[容器终止前执行 preStop 钩子]

五、Pause 容器（Infra 容器）

Pod 中的多个容器之所以能共享网络和存储，靠的是一个用户通常看不见的”幕后容器”——Pause 容器（也叫 Infra 容器）。

当一个 Pod 被创建时，kubelet 会先启动一个 Pause 容器，由它来创建并持有整个 Pod 的 Network Namespace 等命名空间。随后，Pod 中的业务容器都以 join 的方式加入 Pause 容器的命名空间。因此：

  • 所有业务容器看到的网络配置完全一致，共享同一个 IP 和端口空间，彼此可通过 localhost 通信。
  • 即使某个业务容器重启，Pod 的网络命名空间依然由 Pause 容器持有，Pod 的 IP 不会改变。
graph TD
    subgraph Pod
        P[Pause 容器\n持有 Network Namespace]
        C1[业务容器 A]
        C2[业务容器 B]
        C1 -- join --> P
        C2 -- join --> P
    end

Pause 容器镜像极小、逻辑简单（启动后就进入休眠），几乎不消耗资源，却是整个 Pod 共享模型的基石。

六、生命周期钩子（Lifecycle Hooks）

Kubernetes 允许为容器注册两个生命周期钩子，让容器在特定时刻执行自定义动作：

  • postStart：在容器创建后立即执行，与容器主进程并行触发（不保证在主进程之前完成）。
  • preStop：在容器被终止之前执行，常用于优雅关闭，例如通知应用停止接收新请求、完成正在处理的任务后再退出。

钩子的执行方式与探针类似，支持 exec 和 httpGet。

七、临时容器（Ephemeral Container）

临时容器是一种用于调试的特殊容器，可以临时加入到一个正在运行的 Pod 中。当线上 Pod 出现问题、而其镜像又是精简版（没有 shell、没有调试工具）时，可以通过 kubectl debug 注入一个带有完整工具链的临时容器，共享目标 Pod 的命名空间进行排查。

临时容器不会自动重启，也不能声明资源和端口，仅用于交互式诊断，问题排查完毕后随之消失。

八、Pod 的创建流程

Pod 的创建流程是 Kubernetes 最核心的内容之一。理解它的关键，是抓住”声明式 + 各组件持续 watch API Server”这一核心思想：用户只描述期望状态，各组件通过监听（watch）API Server 的资源变化来协同工作，而不是被上层逐级下命令。

8.1 前提：所有组件都在 watch API Server

在集群开机启动后，各组件就进入了持续监听状态：

  • 每个工作节点上的 kubelet：一直 watch API Server，关注”有没有属于自己节点的 Pod 要处理”。
  • Master 上的 scheduler（调度器）：一直 watch API Server，关注”有没有还没分配节点的 Pod 需要调度”。
  • Master 上的 controller-manager（控制器管理器）：一直 watch API Server，关注”有没有需要它处理的资源对象”。

它们彼此之间不直接通信，全部围绕 API Server 展开工作。

8.2 完整创建流程（以创建一个 tomcat 应用为例）

以执行 kubectl create deploy tomcat --image=tomcat 为例，完整流程如下：

  1. 用户执行 kubectl create deploy tomcat，命令发送到 API Server。
  2. API Server 收到命令后，把这个 Deployment 的信息写入 etcd 存储。
  3. etcd 存储成功后，将结果上报给 API Server。
  4. controller-manager 通过 watch 感知到有新的 Deployment，于是根据它生成对应的 Pod 信息（此时 Pod 还没有被分配到具体节点）。
  5. controller-manager 把生成的 Pod 信息交给 API Server，API Server 再次写入 etcd。
  6. etcd 存储成功后上报给 API Server。
  7. scheduler 通过 watch 感知到有一个未调度的 Pod，于是执行调度决策，选出最合适的节点（例如选中 node-02），并把调度结果（即 Pod 该运行在哪个节点上）交给 API Server。
  8. API Server 把这个调度结果再次写入 etcd，etcd 存储成功后上报给 API Server。
  9. 各节点的 kubelet 都在 watch API Server。node-02 上的 kubelet 通过 watch 发现这个 Pod 被分配给了自己。
  10. node-02 的 kubelet 于是调用本节点的容器运行时，启动这个 Pod（创建并运行容器）。
  11. 启动完成后，node-02 的 kubelet 把 Pod 的运行状态汇报给 Master（API Server），API Server 再写入 etcd 记录最新状态。

8.3 watch 机制总结

从上面的流程可以提炼出 Kubernetes 组件协作的固定套路，可以概括为一个不断重复的四步循环：

  1. API Server 接收命令：接收来自用户或其它组件的请求。
  2. 与 etcd 交互存储信息：API Server 把信息写入 etcd（API Server 是唯一直接与 etcd 交互的组件）。
  3. etcd 上报 API Server：存储完成后把结果返回给 API Server。
  4. 上层组件 watch 后动作并反馈：controller-manager、scheduler、kubelet 等组件通过 watch 感知到变化，做出各自的动作，再把结果反馈回 API Server，进入下一轮循环。

正是靠这套”watch + 反馈”的循环，Kubernetes 才能让各组件解耦协作，共同推动 Pod 走向用户描述的期望状态。

九、Pod 的终止

Pod 代表在集群节点上运行的进程，当这些进程不再需要时，应当让它们优雅地关闭，而不是被粗暴地强制杀死。因此当用户请求删除 Pod 时，集群会记录并跟踪一个体面终止（graceful termination）周期，而不是直接强制杀掉进程。

体面终止的大致过程如下：

  1. 用户发出删除 Pod 的请求后，kubelet 会向 Pod 中容器的主进程发送 SIGTERM 信号，同时带上一个体面终止的超时限期（grace period），告知容器”请在这段时间内自行退出”。
  2. 这个信号是经由容器运行时异步处理的，因此各容器收到信号的先后顺序不保证。
  3. 许多容器运行时会遵循容器镜像中定义的 STOPSIGNAL：如果镜像里指定的停止信号与 SIGTERM 不同，运行时会发送镜像里定义的 STOPSIGNAL 而不是 SIGTERM。
  4. 如果超过了体面终止限期容器仍未退出，容器运行时会向剩余的进程发送 SIGKILL 信号，强制终止它们。
  5. 所有容器终止后，该 Pod 会从 API Server 中被移除。
  6. 特殊情况：如果在等待进程终止期间，负责管理这些进程的 kubelet 或容器运行时发生了重启，集群会从头开始重试整个终止流程，并重新赋予 Pod 完整的体面终止限期。
graph TD
    A[用户请求删除 Pod] --> B[集群跟踪体面终止周期]
    B --> C[kubelet 向主进程发送 SIGTERM<br/>并带上体面终止超时限期]
    C --> D{镜像是否定义 STOPSIGNAL?}
    D -->|不同于 SIGTERM| E[运行时改发 STOPSIGNAL]
    D -->|未定义或相同| F[使用 SIGTERM]
    E --> G{在超时限期内退出?}
    F --> G
    G -->|是| I[Pod 从 API Server 移除]
    G -->|否，超过限期| H[运行时发送 SIGKILL 强制终止]
    H --> I

简单来说，Kubernetes 优先给应用一段时间”体面收尾”（SIGTERM / STOPSIGNAL），只有在超时后才会”强制关停”（SIGKILL），这样能尽量避免请求丢失、数据损坏等问题。

Kubernetes hostPath 卷详解 本文是《存储：Volume、持久卷与配置容器》中 hostPath 小节的深入展开，聚焦生产实践中的用法、安全风险与排障。 一、基本概念hostPath 是 Kubernetes 提供的一种卷类型，它允许将宿主机的文件系统路径挂载到 Pod 中。这使得 Pod 能够直接访问宿主机上的文件、目录或设备。 正因为它直接打通了容器与宿主机的文件系统边界，hostPath 既强大又危险——用对了是日志采集、节点监控的利器，用错了会带来严重的安全风险（后文详述）。 二、核心用途 访问宿主机系统日志：如 /var/log。 访问节点特定数据：如节点配置、证书等。 开发调试：在开发环境中快速访问宿主机文件。 特殊系统组件：如监控代理、日志收集器等需要访问宿主机资源的组件。 三、配置语法12345volumes: - name: volume-name hostPath: path: "/absolute/path/on/host" # 必须是宿主机上的绝对路径 type: Director...
