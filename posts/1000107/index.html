高级运行时——以 Containerd 和 CRI - O 为例

本文难度系数较大，以containerd为例介绍了高级运行时最重要的功能，高级运行时向下和OCI规范、低级运行时相关，向上和镜像拉取、镜像存储相关，建议结合相关知识点食用，多做实验加深理解。

一、高级运行时

回顾：高级运行时 vs 低级运行时

首先，回顾一下两个关键概念：

  1. 低级运行时 (Low-Level Runtime)：
    • 职责：直接与操作系统内核交互，负责最底层的操作，即创建和运行容器进程。它接收一个包含了 rootfs 路径和配置的 JSON 文件（OCI runtime-spec），然后调用 clone、unshare 等系统调用去启动一个具有正确隔离（namespace、cgroups）的进程。
    • 代表：runc（是 OCI 标准的参考实现）、runhcs（用于 Windows）、crun、kata-runtime。
  2. 高级运行时 (High-Level Runtime)：
    • 职责：管理容器的整个生命周期。包括镜像的传输、管理、解压、文件系统快照的维护，以及最终调用低级运行时会执行容器。它解决了“如何从镜像到运行的容器”这个完整问题。
    • 代表：Containerd、CRI-O。

常见的两种高级运行时

1. Containerd：纯粹的高级运行时

  • 定位：它是一个行业标准的核心容器运行时，专注于简单性、健壮性和可移植性。它的设计目标就是成为一个可以被更大系统（如 Docker 或 Kubernetes）嵌入的组件。
  • 功能：它直接完成了高级运行时的所有“第一要务”：镜像拉取、存储、管理快照、生成 config.json，并通过 containerd-shim 调用 runc。
  • 接口：它提供自己的 gRPC API（不是 CRI）。Docker 通过这个原生 API 与它通信。Kubernetes 的 kubelet 组件通过一个名为 containerd-cri 的插件与 Containerd 通信。这个插件实现了 Kubernetes CRI (Container Runtime Interface) 接口。

2. CRI-O：Kubernetes 原生的高级运行时

  • 定位：它是一个轻量级、专注于 Kubernetes 的高级运行时。它的唯一目的就是实现 Kubernetes CRI (Container Runtime Interface) 接口。它本身也是 Containerd 的一个竞争对手。
  • 功能：它实现了和 Containerd 一样的高级运行时功能（镜像、快照、运行时管理），但架构更简单，没有任何与 Kubernetes 无关的额外功能。
  • 接口：它只实现 Kubernetes CRI 接口。Kubelet 直接通过 CRI gRPC 协议与它通信。

二、高级容器运行时的第一要务：打通镜像与运行时的鸿沟

容器技术的核心在于一致性：无论在何处、何时运行，同一个容器镜像都应产生相同的行为。高级容器运行时（如 Containerd、CRI-O）正是实现这种一致性的基石。它们的首要职责，就是作为一座高效的桥梁，将静态的、标准化的OCI镜像（OCI Image Spec） 转换为动态的、可执行的容器运行时配置（OCI Runtime Spec）。

这个过程的核心输出是两样东西：

  1. rootfs：容器的根文件系统，即镜像内容展开后的最终形态。
  2. config.json：容器的运行时配置文件，定义了隔离 namespace、cgroups、权限、环境变量等。

一、从镜像到配置：config.json的生成

config.json（即OCI运行时规范文件）的生成相对直接，是一个“混合”的过程：

  1. 基础模板：运行时首先会创建一个符合OCI标准的基础配置模板。
  2. 注入镜像配置：从镜像的配置清单（Image Config） 中提取关键信息，填充到模板中。这包括：
    • 默认启动命令：Entrypoint 和 Cmd
    • 环境变量：Env
    • 工作目录：WorkingDir
    • 用户信息：User
  3. 融入运行时指令：接收来自客户端（如Docker CLI或Kubelet）的额外指令，覆盖或补充镜像本身的配置。例如：
    • 覆盖启动命令（docker run ... /bin/bash）
    • 添加新的环境变量（-e MY_VAR=value）
    • 设置资源限制（--memory, --cpu）

最终生成的config.json是一个融合了OCI标准规范、镜像默认配置和用户自定义指令的最终蓝图，它将直接交给低级运行时（如runc）来创建容器。

二、从镜像到根文件系统：rootfs的构建

这是高级运行时最复杂、最核心的任务。其目标是将镜像中多层、压缩的**layer.tar文件，转换为一个完整的、可供容器进程直接使用的rootfs**目录。这个过程面临着三大挑战，其解决之道完美体现了容器技术的精妙之处。

挑战与解决方案

挑战一：如何高效地存储和复用解压后的文件系统层（fs layers）？

  • 问题：如果每次创建容器都从头解压所有镜像层，效率极低，浪费磁盘和CPU资源。
  • 解决方案：内容寻址存储与链式ID（Chain ID）
    • 镜像的每一层都有一个唯一的DiffID（即该层tar包解压后内容的SHA256哈希值）。
    • 高级运行时在解压某一层时，会利用上一层的ChainID和本层的DiffID计算出一个新的ChainID（ChainID_n = SHA256(ChainID_n-1 + " " + DiffID_n)）。
    • 这个ChainID即作为该文件系统层（fs layer） 的唯一索引ID。磁盘上会有一个目录（如/var/lib/containerd/io.containerd.content.v1.content/blobs/sha256/）专门存储这些以ID命名的fs layers。
    • 好处：只要镜像层内容不变，其DiffID和最终的ChainID就绝不会变，从而实现全局复用。不同镜像可以共享相同的底层，极大地节省空间。

挑战二：如何维护文件系统层之间的父子关系？

  • 问题：镜像层是堆叠的，每层都基于其下层进行修改，必须维护这种层次关系才能正确组装出最终视图。
  • 解决方案：在元数据中记录父层引用
    • 如上文所述，每个fs layer的ChainID本身就编码了其父层的信息。
    • 此外，高级运行时（如Containerd）会在其元数据库（Metastore，如BoltDB） 中显式地记录每个快照的父层是谁。Snapshotter插件负责管理这些依赖关系。

挑战三：如何保证运行时的写入操作不破坏共享的基础镜像层？

  • 问题：多个容器可能共享同一个基础镜像层。如果一个容器的写入操作修改了底层，会影响到所有其他容器，违背了隔离性原则。
  • 解决方案：写时复制（Copy-on-Write, CoW）与联合文件系统（UnionFS）
    • 高级运行时在创建容器时，永远不会直接在任何共享的fs layer上进行写入。
    • 它会基于最顶层的镜像fs layer，创建一个新的、空的可写层（通常称为“容器层”或“快照”）。
    • 然后，使用UnionFS（如OverlayFS、-AUFS）将所有只读的镜像层和这一个可写的容器层合并（挂载）到一个单独的目录（rootfs）中。
    • 过程：容器进程对文件的任何读取请求，都会由UnionFS从最上层的可用版本中透明地返回。写入请求则会触发CoW：
      • 如果要写入的文件在底层是只读的，UnionFS会首先将该文件复制到可写层，然后在副本上进行修改。
      • 删除文件则是在可写层中创建一个“白障（whiteout）”文件来标记删除。
    • 结果：每个容器都有自己的可写层，所有的更改都被隔离在这个层内，完美保护了共享的底层镜像不被污染。

三、容器元数据（Container Meta）：管理的基石

为了持久化地管理容器，高级运行时引入了容器元数据（Container Meta） 的概念。这是一个包含容器所有信息的数据库记录，通常包括：

  • 容器ID
  • 所使用的镜像引用
  • 生成并使用的OCI spec.json 路径
  • 对应的快照（Snapshot）信息（即构成其rootfs的各层和可写层ID）
  • 标签（Labels） 和注解（Annotations）
  • 运行时信息（使用哪个shim和低级运行时）

元数据的存在是高级运行时强大管理能力的基础。它使得：

  • 快速恢复：守护进程（如Containerd）重启后，只需读取元数据库即可重建所有容器的状态，无需知道容器进程的具体细节。
  • 高效操作：所有针对容器的操作（如exec、logs、stop）都可以通过容器ID查询元数据，快速定位到对应的运行时实例和文件系统。
  • 状态持久化：容器的状态（运行中、已停止、已暂停）得以持久化保存。

总结

高级容器运行时的“第一要务”，远不止是简单地解压文件和调用runc。它是一个复杂的数据工程和系统设计问题，核心在于：

  1. 标准化：遵循OCI规范，保证生态的一致性。
  2. 效率：通过内容寻址、链式ID和共享机制，最大化利用磁盘和内存资源。
  3. 隔离性：利用UnionFS和Copy-on-Write技术，确保容器间的隔离与安全性。
  4. 可管理性：通过容器元数据抽象，实现对容器生命周期的精细、稳定和高效的控制。

正是这些精妙的设计，使得我们能够轻松地一句命令docker run或一个YAML文件kubectl apply就能启动一个容器，而无需关心背后复杂的镜像拉取、层管理和文件系统组装过程。

三、Containerd 简介

核心设计理念

Containerd 的设计遵循两个核心原则：

  1. 高度模块化与可插拔：所有功能都由独立的插件（Plugin） 实现，并通过 gRPC 或更轻量的 TTRPC 协议提供服务。这种设计使得：
    • 易于嵌入：可以轻松地集成到 Docker、Kubernetes 等更大的系统中。
    • 功能可定制：用户可以用 Go 语言编写自己的插件来扩展功能。
    • 跨平台：核心逻辑与平台无关，通过不同的插件实现来支持 Linux、Windows 等系统。
  2. 客户端/服务端分离：核心功能作为一个常驻守护进程（containerd），所有操作都通过高效的 RPC 调用进行。这带来了一个利弊：虽然获得了清晰的架构和稳定性，但模块间的通信开销比简单的函数调用更大。

  • API 层 (gRPC Server)
    • 作用：提供唯一的对外通信接口。所有客户端（如 Docker、Kubernetes CRI Plugin）都通过 gRPC 协议与 Containerd 交互。
    • 好处：保证了接口的稳定性和版本控制。
  • 核心组件 (Core)
    • 作用：它不是功能实现者，而是系统的“大脑”。负责协调插件的生命周期、依赖注入和 RPC 路由。它发现了所有插件并将其组织成一个有机整体。
  • 元数据存储 (MetaStore)
    • 作用：存储所有镜像、容器、快照的元数据（索引和关系信息）。
    • 实现：默认使用 BoltDB（一个轻量级的嵌入式键值数据库），每个命名空间（Namespace）都有一个独立的数据库实例。
  • 核心功能插件 (Plugins)
    • Content：管理镜像层（Layer）等内容的存储，内容以 SHA256 哈希值为索引存储在磁盘上。负责校验和读写。
    • Images：管理镜像的元数据（如 Manifest、Config），将镜像名称（Repository Tag）映射到具体的 Manifest 和 Layer，信息存储在 MetaStore 中。
    • Snapshots：管理容器文件系统的快照。每个容器镜像层解压后就是一个快照，容器运行时所需的可写层（RW Layer）也是一个快照。它通过不同的驱动（Driver） 支持多种联合文件系统，如 overlayfs、aufs、btrfs 等。
    • Containers：管理容器的元数据，如容器名称、使用的镜像、运行时配置等。这些信息也存储在 MetaStore 中。
    • Tasks：这是容器运行时管理的核心。它将静态的容器（Container）变为运行的进程（Task）。负责调用下一级的 containerd-shim 来启动和管理容器进程。
  • 运行时与 Shim (containerd-shim)
    • 这是 Containerd 架构中至关重要的一环，它实现了守护进程与容器进程的解耦。
    • 工作流程：当 Tasks 插件需要启动一个容器时，它会根据配置的运行时（如 io.containerd.runc.v2）启动一个独立的 containerd-shim 进程。
    • shim 的职责：
      • 作为容器进程的实际父进程，托管容器进程。
      • 保持容器的 STDIO 流打开，即使 Containerd 守护进程重启，容器也不会被终止。
      • 将容器的退出状态和事件报告给 Containerd。
      • 最终调用真正的低级 OCI 运行时（如 runc） 来创建容器。
    • 好处：Containerd 可以随时升级或重启，而不会影响正在运行的容器。
  • 命名空间 (Namespace)
    • 作用：提供逻辑上的隔离。所有插件都支持 Namespace。
    • 示例：Kubernetes 使用 k8s.io 命名空间，Docker 使用 moby 命名空间。它们之间的镜像、容器、快照等资源是完全隔离的，互不可见。这使得一套 Containerd 实例可以同时为多个上层系统服务。

核心工作流程（以启动容器为例）

  1. 拉取镜像（Pull Image）：
    • 客户端通过 gRPC 发起 Pull 请求。
    • Images 插件解析镜像索引（Index）和清单（Manifest）。
    • Content 插件下载镜像层（Layer）数据包并存储到磁盘，以 SHA256 校验和作为索引。
    • 元信息被存入 MetaStore。
  2. 准备容器文件系统（Prepare Snapshot）：
    • 客户端发起创建容器请求。
    • Snapshots 插件根据指定镜像的各层，使用 overlayfs 等驱动，组装成一个完整的、可供容器使用的 rootfs。最上层会创建一个新的可写快照层。
  3. 创建容器（Create Container）：
    • Containers 插件将容器的运行时配置（命令、环境变量等）和与镜像、快照的关联关系存入 MetaStore。此时容器只是一个静态对象。
  4. 启动容器（Start Task）：
    • 客户端发起启动任务请求。
    • Tasks 插件处理请求，准备好 OCI 运行时规范文件（spec.json）。
    • Runtime Shim Launcher 启动一个 containerd-shim 进程。
    • shim 进程从 Snapshots 插件获取 rootfs 路径，调用 OCI 运行时（如 runc） 来创建并启动容器进程。
    • shim 进程将容器进程的 PID 和状态通过 TTRPC 返回给 Tasks 插件。
  5. 生命周期管理（Lifecycle Management）：
    • 后续对容器的所有操作（如 exec、stop、pause）都通过 Tasks 插件经由 shim 进程来完成。
    • Events 插件在整个过程中向订阅的客户端发送事件通知。

总结

Containerd 通过其模块化、基于插件的架构，提供了一个高效、稳定且跨平台的容器运行时基础。它将复杂的容器管理功能分解成一系列职责单一、通过清晰 API 通信的组件。containerd-shim 的设计是其实现稳定性的关键，它完美地隔离了守护进程和容器进程的生命周期。正是这种优秀的设计，使其能够成为 Docker 和 Kubernetes 等主流平台的坚实基础。

3. 镜像解析与分层合并（rootfs 生成）

目标：运行一个容器，查看 Containerd 如何合并分层并生成 rootfs。

核心概念：镜像分层与 Union FS

容器镜像通常由多个只读层（Layers） 组成，这种分层结构带来了很多好处：比如共享通用层可以节省磁盘空间和传输带宽5。当我们启动一个容器时，容器运行时（如 Containerd）会将这些只读层与一个可写的顶层（容器层）合并，形成一个统一的文件系统视图（即 rootfs），提供给容器进程。这个过程依赖于联合文件系统（Union File System） 技术5。

OverlayFS 是 Linux 内核支持的一种联合文件系统，也是 Containerd 常用的存储驱动之一。它主要涉及以下目录2：

  • LowerDir：只读的镜像层。一个镜像可能有多个 LowerDir，对应 Dockerfile 中的每条指令产生的层。
  • UpperDir：可写的容器层。所有对容器文件系统的修改（写入、删除）都发生在这里。
  • MergedDir：最终的合并视图。这是 LowerDir 和 UpperDir 联合挂载后的结果，也是容器内进程看到的文件系统根目录 (rootfs)。
  • WorkDir：OverlayFS 内部使用的工作基础目录，用于处理如文件重命名等操作所需的临时工作2。

理解 rootfs 的生成过程

当你运行 ctr run 时，Containerd 大致做了以下几步：

  1. 解析镜像：读取 nginx:alpine 镜像的配置清单（Manifest），获取其所有的层级信息（Layers）。
  2. 准备快照：确保所有镜像层都已经作为只读快照（LowerDir） 存在本地。如果本地没有，会先从注册表拉取。
  3. 创建容器可写层：为这个新容器创建一个可写快照（UpperDir）。
  4. 联合挂载：使用 OverlayFS，将所有的只读层（LowerDir） 和可写层（UpperDir） 联合挂载到一个指定的目录（MergedDir），这个目录就是容器的 rootfs。
  5. 运行容器：调用 runc 等底层运行时工具，在这个准备好的 rootfs 中，按照镜像配置启动容器内的初始进程。

验证“写时复制（CoW）”机制

写时复制（Copy-on-Write） 是一种高效的资源管理策略。其核心思想是：只有在真正需要写入数据时，才会复制原始数据副本，在此之前，所有对象共享同一份原始数据。

在容器技术中的体现：

  1. 镜像层（只读）：容器镜像的每一层都是只读的（LowerDir）。当多个容器由同一个镜像启动时，它们共享这些相同的只读层。这极大地节省了磁盘空间和内存（因为操作系统可以通过“页共享”在内存中共享相同的代码段）。
  2. 容器层（可写）：每个容器实例都有自己的可写层（UpperDir）。
  3. CoW 过程：
    • 读操作：当容器进程需要读取一个文件时，OverlayFS 驱动会从下往上在各个层中查找该文件。一旦找到，就会返回文件内容。因为所有层都是只读的（除了最上层），所以读取操作非常高效且无需复制。
    • 写操作：当容器进程第一次要修改一个存在于下层只读镜像中的文件时，CoW 机制就会被触发：
      • 复制：OverlayFS 首先将该文件的整个副本从只读层复制到容器的可写层（UpperDir）。
      • 写入：然后，所有的修改只会作用于可写层中的这个文件副本上。
    • 删除操作：当容器中删除一个存在于下层的文件时，OverlayFS 会在可写层（UpperDir）中创建一个特殊的**“白底”（whiteout）文件**（通常是一个字符设备文件，主次设备号为 0:0）来标记该文件已被删除，从而在合并视图（MergedDir）中隐藏它。

优点：

  • 节省空间：成千上万的容器可以共享同一个基础镜像，而无需为每个容器复制一份。
  • 加快启动速度：容器无需等待整个文件系统解压，瞬间即可启动。
  • 提高效率：镜像分层构建、传输和存储都更加高效。

1. CRI-O 核心概念解析

CRI-O 是专为 Kubernetes（K8s） 设计的轻量级开源容器运行时，核心定位是实现 K8s 的容器运行时接口（CRI），同时兼容开放容器计划（OCI）标准，是 Docker、containerd 的轻量化替代方案。

1.1 核心背景与版本特性

  • 起源与演进：2016 年始于 K8s 孵化器项目，初名为“开放容器倡议守护进程（OCID）”，2017 年发布 1.0.0 正式版。
  • 版本对齐规则：严格遵循 K8s 发布周期，确保版本兼容性（如 K8s 1.15 可安全搭配 CRI-O 1.15），降低生产环境适配风险。
  • 核心优势：专注于实现 CRI 这一单一核心任务，无冗余功能，资源占用更低，适合生产环境中 K8s 工作负载的轻量化部署。

1.2 技术架构与工作原理

CRI-O 遵循 UNIX“单一职责”理念，架构分为三层，各组件分工明确：

架构层级 核心组件 功能作用
前端（API 层） gRPC API 服务 对外提供 CRI 接口，接收 K8s 或 crictl 的请求
中间层（协调层） CRI-O 主程序 + 核心库 协调前后端交互，依赖 containers/storage（容器存储）、containers/image（镜像管理）等库处理核心逻辑
后端（执行层） runc 基于 OCI 标准的底层容器运行时，负责容器的创建、启动、停止等基础管理操作
