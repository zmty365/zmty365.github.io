k8s 之 fieldsV1 简单介绍

发表于2026-08-07|Kubernetes
|总字数:1.1k|阅读时长:4分钟|浏览量:

用 client-go 或 controller-runtime 的 Client 查询一个 Deployment，把结果打印成 YAML，常常会发现里面多了一大坨 managedFields，而同样的对象用 kubectl get -o yaml 却看不到。这块内容里的 fieldsV1 到底是什么？为什么两边不一致？本文做一个简单的梳理。

一、为什么会出现 fieldsV1

1.1 Server-Side Apply（SSA）

在 Kubernetes 1.18 之前，kubectl apply 采用的是 Client-Side Apply：客户端在本地计算差异（依赖 last-applied-configuration 注解），再把结果发给 API Server。这种方式有个问题——多个客户端（或控制器）同时修改同一个对象时，无法准确判断「某个字段到底是谁在管」，容易互相覆盖。

Kubernetes 1.18 正式引入了 Server-Side Apply（SSA） 机制，把「字段所有权」的计算搬到了服务端。API Server 会记录每个字段是被哪个「管理者」（manager）修改的，从而在多方写同一对象时精确地检测和处理冲突。

1.2 managedFields

为了实现 SSA，每个资源对象的 metadata 里都多了一个 managedFields 字段，记录了每个字段的管理者信息——例如哪个客户端、用哪种操作（Apply / Update）、在什么时间修改了哪些字段。

1.3 fieldsV1

fieldsV1 就是 managedFields 里描述「具体哪些字段被这个 manager 管理」的部分，它用一种树状结构精确地标记出被管理的字段路径。

三、为什么查到的 YAML 和 kubectl 看到的不一样

同一个对象，通过不同途径查询，managedFields 的可见性不同：

graph TB
    A[资源对象] --> B[kubectl get -o yaml]
    A --> C[client-go / controller-runtime Client]
    B --> D[默认隐藏 managedFields]
    C --> E[默认包含 managedFields]

3.1 默认行为

managedFields 属于内部元数据，对日常查看资源的用户通常没有用，所以 kubectl get、kubectl describe 默认会把它隐藏起来。

3.2 显式查询

如果你通过 client-go 或其他 SDK 直接查询资源对象，API Server 返回的完整对象里是包含 managedFields 的，SDK 不会替你隐藏。

3.3 YAML 序列化

当你把这个完整对象序列化成 YAML 时，managedFields（以及里面的 fieldsV1）自然也会被一起打印出来。这就是「代码里查出来的 YAML 比 kubectl 多一大坨」的原因。

六、小结

  • fieldsV1 是 managedFields 的一部分，用树状结构记录字段的所有权信息，它是 Server-Side Apply 机制的基础数据。
  • kubectl 默认隐藏 managedFields，而通过 client-go 直接查询时会包含它——这就是两边 YAML 不一致的原因。
  • 如果需要生成与 kubectl 一致的干净 YAML，可以在序列化前通过 SetManagedFields(nil) 移除它。
