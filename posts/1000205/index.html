Kubernetes 网络

一、Kubernetes 的三种 IP

Kubernetes 中有三种不同层面的 IP，理解它们的区别是理解 K8s 网络的基础。

  • Node IP：Node 节点的 IP 地址

    Node IP 是 Kubernetes 集群中节点的物理网卡 IP 地址，所有属于这个网络的服务器之间都能通过这个网络直接通信。

  • Pod IP：Pod 的 IP 地址

    Pod IP 是每个 Pod 的 IP 地址，它由集群配置的 CNI 插件（如 Flannel、Calico 等）根据规划好的 Pod 网段分配，通常构成一个覆盖整个集群的虚拟网络。集群内的所有 Pod 都在同一个扁平的网络平面内，可以直接通过 Pod IP 互相通信。

  • Cluster IP：Service 的 IP 地址（Service Virtual IP，service vip）

    Cluster IP 是一个虚拟 IP，专门服务于 Kubernetes 的 Service 对象，由 Kubernetes 管理和分配。它有几个重要特点：

    • 实际的消费者 Pod 通常并不直接调用 Service 的 Cluster IP，而是先调用服务名。因为 Cluster IP 也会变（例如针对 TEST / UAT / PROD 等不同环境的发布，Cluster IP 会不同），而服务名一般不变。
    • Cluster IP 仅仅作用于 Kubernetes Service 这个对象，并由 Kubernetes 管理和分配 IP 地址。
    • Cluster IP 无法被 ping，它没有一个”实体网络对象”来响应。
    • Cluster IP 只能结合 Service Port 组成一个具体的通信端口，单独的 Cluster IP 不具备通信的基础，并且它们属于 Kubernetes 集群这样一个封闭的空间。

二、Service

一个 Pod 只是一个运行服务的实例，随时可能在一个节点上停止，又在另一个节点以一个新的 IP 启动一个新的 Pod，因此不能以确定的 IP 和端口号提供服务。要稳定地提供服务，就需要服务发现和负载均衡能力。

服务发现完成的工作，是针对客户端访问的服务，找到对应的后端服务实例。在 K8s 集群中，客户端需要访问的服务就是 Service 对象。每个 Service 会对应一个集群内部有效的虚拟 IP，集群内部通过虚拟 IP 访问一个服务。

在 Kubernetes 集群中，微服务的负载均衡是由 Kube-proxy 实现的。Kube-proxy 是 Kubernetes 集群内部的负载均衡器，是一个分布式代理服务器，在每个节点上都有一个。这一设计体现了它的伸缩性优势：需要访问服务的节点越多，提供负载均衡能力的 Kube-proxy 就越多，高可用节点也随之增多。相比之下，如果在服务器端做一个反向代理来做负载均衡，还要进一步解决反向代理自身的负载均衡和高可用问题。

Service 是 K8s 服务的核心，它屏蔽了服务细节，统一对外暴露服务接口。举个例子：一个服务 A 部署了 3 个副本，也就是 3 个 Pod；对于用户来说，只需要关注一个 Service 的入口即可，而不需要操心究竟应该请求哪一个 Pod。优势非常明显：

  • 一方面，外部用户不需要感知因 Pod 上服务意外崩溃、K8s 重新拉起 Pod 而造成的 IP 变更，也不需要感知因升级、变更服务带来的 Pod 替换而造成的 IP 变化；
  • 另一方面，Service 还可以做流量负载均衡。

2.1 Service 的四种类型

Service 有四种类型：ClusterIP、NodePort、LoadBalancer、ExternalName，下面逐一介绍。

ClusterIP

ClusterIP 是 Service 默认的类型 / 机制。如上面的 yaml 文件，如果并没有指定 type，那么执行 kubectl create -f service-demo.yaml 之后就会得到一个 ClusterIP 类型的 Service。

ClusterIP 类型的 Service 会提供一个 CLUSTER-IP 和 PORT(S)，能够允许 K8s 内部相同 namespace 下的任何 Pod 访问。

ClusterIP 服务注册发现流程：

  1. 在服务 Pod 实例发布时，Kubelet 负责启动 Pod 实例，启动完成后，Kubelet 会把服务的 Pod IP 列表汇报注册到 Master 节点。
  2. 使用 ClusterIP 发布 Service，K8s 会为服务分配 ClusterIP，同时会在集群中创建出一个同名的 Endpoints 对象，用于存储该 Service 下的 Pod IP。
  3. 在服务发现阶段，运行在每个节点的 Kube-Proxy 会监听 Service 和 Endpoints，发现 ClusterIP 和 Pod IP 列表的映射关系，并在各自的 node 节点设置相关的 iptables 或 IPVS 转发规则，指示在接收到目标为某个 ClusterIP 的请求时，进行负载均衡并转发到对应的 Pod IP 上。
  4. 集群内部的消费者通过 ClusterIP 发起调用，这个请求会被本地 iptables 机制截获，然后通过负载均衡转发到目标服务 Pod 实例上。

ClusterIP 仅在 Kubernetes 集群内部可用，不能从集群外部直接访问。这是为了安全和隔离，确保只有集群内部的流量可以访问这些服务。

NodePort

NodePort 可以为外部提供服务。

NodePort 即节点 Port，通常在部署 Kubernetes 集群时会预留一个端口范围用于 NodePort，其范围默认为 30000 ~ 32767 之间的端口。定义 NodePort 类型的 Service 资源时，需要使用 .spec.type 进行明确指定。

NodePort 实际是在 Pod 所在的物理机器上开了一个端口，让外部流量从这个端口先导流到自己的 port，再导入 targetPort（也就是 Pod 的端口）。

NodePort 服务注册发现流程：

  1. 在服务 Pod 实例发布时，Kubelet 负责启动 Pod 实例，启动完成后把 Pod IP 列表汇报注册到 Master 节点。
  2. 使用 NodePort 发布服务并指定一个 30000 ~ 32767 范围内的端口，所有 Worker 节点都会对这个端口进行监听。K8s 在集群中创建出一个同名的 Endpoints 对象，用于存储该 Service 下的 Pod IP。
  3. 运行在每个节点的 Kube-Proxy 会监听 Service 和 Endpoints，发现 ClusterIP 和 Pod IP 列表映射关系，并在各自的 node 节点设置相关的 iptables 或 IPVS 转发规则。
  4. 当外部流量到达任意节点的 NodePort 端口时，kube-proxy 配置的规则会将流量转发到后端的 Service。

需要注意：NodePort 本身并不提供负载均衡功能。NodePort 只是使服务可以通过节点上的静态端口对外访问，而负载均衡是由 Service 本身（通过 kube-proxy 设置的 iptables 或 IPVS 规则）来实现的。

LoadBalancer

LoadBalancer 其实就是在客户访问的最前端加入一个负载均衡器。它与 NodePort 的对比如下：

维度 NodePort LoadBalancer
性能 受限于节点数量和端口范围，适合小型集群 利用云厂商的高性能负载均衡器，适合大型集群
安全性 暴露节点 IP 和端口，安全性较低 由云厂商管理外部 IP 和端口，安全性较高
成本 无需额外费用，成本较低 需支付云厂商的负载均衡器费用，成本较高
灵活性 配置简单，灵活性较低 支持多种负载均衡策略，灵活性较高

LoadBalancer 的工作依赖第三方负载均衡器。例如安装 Ingress 控制器时，会创建一个类型为 LoadBalancer 的 Service。新创建的 Service 的 EXTERNAL-IP 状态是 <pending>——如果没有可用的负载均衡器，它会一直处于 pending 状态。

IP 解析：

  • Cluster IP（如 10.233.50.2）：服务在集群内部的虚拟 IP，集群内其他 Pod 可通过它访问该服务；自动分配，且在服务生命周期内保持不变。
  • External IP（显示为 <pending>）：对于 LoadBalancer 类型的服务，这是云厂商分配的外部 IP。在自建集群（如使用 MetalLB）中，可能需要额外配置才会分配；<pending> 表示尚未分配外部 IP。

端口类型解析： 一个服务可能暴露多个端口，每种端口含义不同：

  • Service Port（如 9091/TCP）：服务在 Cluster IP 上暴露的端口，集群内部访问时使用。
  • TargetPort（如 9091/TCP）：实际 Pod 上应用程序监听的端口，流量最终会被转发到这里。
  • NodePort（如 19650/TCP）：当服务类型为 NodePort 或 LoadBalancer 时，Kubernetes 会在每个节点上开放这个端口。即使没有外部负载均衡器，也可以通过任意节点的 IP + NodePort 访问服务。

  • 在生产环境中，通常会配合 Ingress 控制器使用，而不是直接暴露多个 NodePort。
  • 在云环境中，LoadBalancer IP 的分配通常需要几分钟时间。

ExternalName

ExternalName 是一种比较特殊的 Service 类型：它不代理到任何 Pod，也不会分配 Cluster IP，而是通过 DNS 的 CNAME 记录把服务名映射到一个外部域名。常用于让集群内的应用以统一的服务名访问集群外部的服务（如外部数据库）。

集群内的 Pod 访问 my-database 时，DNS 会将其解析为 db.example.com。由于只是 DNS 层面的别名，ExternalName 不涉及端口转发和负载均衡。

2.2 两种特殊的 Service

Pod 会话保持（粘性会话）

Service 资源还支持 Session affinity（粘性会话） 机制，可以将来自同一个客户端的请求始终转发至同一个后端 Pod 对象。这意味着它会影响调度算法的流量分发，进而降低负载均衡的效果。

因此，当客户端访问 Pod 中的应用程序时，如果有基于客户端身份保存某些私有信息、并基于这些私有信息追踪用户活动等需求时，就应该启用 session affinity 机制。

Service affinity 的效果仅在一段时间内生效，默认值为 10800 秒，超出时长后客户端再次访问会重新调度。该机制仅能基于客户端 IP 地址识别客户端身份，它会将经由同一个 NAT 服务器进行源地址转换的所有客户端识别为同一个客户端，由此可知其调度效果并不理想。

Service 资源通过 .spec.sessionAffinity 和 .spec.sessionAffinityConfig 两个字段配置粘性会话。.spec.sessionAffinity 用于定义要使用的粘性会话类型，仅支持 None 和 ClientIP 两种属性值：

  • None 就是随机访问，也是默认值。
  • ClientIP 是把来自同一个客户端的请求调度到同一个 Pod 中。

Headless Service

有时不需要或不想要负载均衡，以及单独的 Service IP。遇到这种情况，可以通过将 spec.clusterIP 指定为 "None" 来创建 Headless Service。

对这类 Service 并不会分配 Cluster IP，kube-proxy 不会处理它们，平台也不会为它们进行负载均衡和路由。DNS 如何实现自动配置，依赖于 Service 是否定义了 selector。这个选项允许开发人员自由寻找他们自己的方式，从而降低与 Kubernetes 系统的耦合性。

Headless Service 常与 StatefulSet 配合使用：为每个有状态 Pod 提供稳定的 DNS 名称，客户端可以直接解析到具体某个 Pod。

2.3 Kube-Proxy 的三种模式

iptables 和 ipvs 都是内核态（基于 netfilter），只有 userspace 模式是用户态。

  • userspace 模式：kube-proxy 在用户空间监听一个端口，并将所有到 Service 的流量转发到后端 Pod。具体来说，kube-proxy 为每个 Service 在节点上打开一个随机端口，并建立 iptables 规则将流量重定向到这个代理端口，然后再由 kube-proxy 转发到后端 Pod。优点是实现简单，缺点是性能较低——每个数据包都要经过用户空间处理，增加了额外的开销和延迟。
  • iptables 模式：这是 kube-proxy 的改进版，相比 userspace 有显著的性能提升。kube-proxy 使用 iptables 设置网络规则，这些规则直接在内核空间处理。当有新的 Service 创建时，kube-proxy 会生成相应的 iptables 规则，定义从 Service IP 和端口到后端 Pod 的 NAT 转发规则。数据包在内核空间直接被转发到后端 Pod，减少了上下文切换，提高了性能。缺点是在处理大量规则时，规则管理和更新可能变得复杂。
  • ipvs 模式：这是 kube-proxy 的最新实现方式，使用 Linux 内核中的 IP Virtual Server（IPVS） 技术。IPVS 是内核中专门用于负载均衡的模块，支持多种调度算法（轮询、最小连接数、最短延迟等）。数据包在内核空间通过 IPVS 直接转发，性能更高，同时支持更多的负载均衡算法和更复杂的网络规则。缺点是需要内核支持 IPVS 模块。

通常情况下默认使用 ipvs 模式，因为它提供了更好的性能和更多的负载均衡选项，尤其是在大规模集群中。

kube-proxy 工作机制小结：

  1. 当用户在集群中创建了含有 label 的 Service 后，集群会同时创建出一个同名的 Endpoints 对象，用于存储该 Service 下的 Pod IP。
  2. 运行在每个 Node 上的 kube-proxy 会实时 watch Service 和 Endpoints 对象，并在各自节点设置相关的 iptables 或 IPVS 规则。
  3. 之后，用户便可以在集群内的 Node 或客户端 Pod 上通过 ClusterIP，经过 iptables 或 IPVS 规则进行路由和转发，最终将请求发送到真实的后端 Pod。

三、Pod 通讯

3.1 Pod 内部通讯

先明确几个网络设备的角色：

  • eth0 是节点主机上的网卡，是支持该节点流量出入的设备，也是支持集群节点间 IP 寻址和互通的设备。
  • 网桥（cni0 / docker0） 是一个虚拟网桥，可以简单理解为一个虚拟交换机，是支持该节点上 Pod 之间进行 IP 寻址和互通的设备。
  • veth 是 Pod 的虚拟网卡，支持该 Pod 内容器互通和对外访问。网桥和 veth 都是 Linux 支持和创建的虚拟网络设备。

Pod 内部的容器是通过共享一个虚拟网卡相互通信的，可以直接通过 localhost 相互访问，而这个虚拟网卡是通过一个特殊的容器 pause 创建的。

3.2 同 Node 的 Pod 通讯

同一节点上的 Pod 都连接在同一个虚拟网桥上，Pod 的 IP 由 CNI 插件从该节点的网段中分配。因为这些 Pod 都连在同一个网桥、处于同一个网段内，它们可以直接进行 IP 寻址和互通。

3.3 不同 Node 的 Pod 通讯

跨节点的 Pod 通讯主要有两种方案：

  • 路由方案

    通过路由设备为 K8s 集群的 Pod 网络单独划分网段，并配置路由器支持 Pod 网络的转发。这种方案依赖底层的网络设备，但不引入额外的性能开销。

  • 覆盖网络（Overlay）方案

    如果底层网络无法控制（比如公有云网络），或者运维团队不支持路由方案，可以采用覆盖网络方案。覆盖网络就是在现有网络之上再建立一个虚拟网络，实现技术有很多，例如 Flannel、Weave Net 等，这些方案大都采用隧道封包技术：Pod 网络的数据包在出节点之前，会先被封装成节点网络的数据包；当数据包到达目标节点，包内的 Pod 网络数据包会被解封出来，再转发给节点内部的 Pod。这种方案对底层网络没有特别依赖，但封包解包会引入额外的性能开销。

四、Ingress

4.1 为什么使用 Ingress

我们可以使用 Ingress 将内部服务暴露到集群外部。它为你节省了宝贵的静态 IP——因为你不需要声明多个 LoadBalancer 服务了。此外，它还可以进行更多的额外配置。

手动配置 Nginx 代理服务：为了让 ClusterIP 类型可以暴露，可以手动配置一个 Nginx 代理服务。例如新增一个名为 service-nginx-proxy 的服务，它是唯一的一个 LoadBalancer 服务，仍然指向一个或多个 Nginx pod endpoints，而之前的另外两个服务则转换为简单的 ClusterIP 服务。这种方式能工作，但需要大量手动配置。

使用 Ingress 代替手动的 Nginx：当正确配置 Ingress 后，即使是 ClusterIP 类型的 Service 也可以暴露给外部。相当于使用了一个预先配置好的 Nginx（Ingress），它已经为我们做了所有的代理重定向工作，省去了大量手动配置。

4.2 Ingress 概述

Ingress 可以简单理解为”Service 的 Service”：它通过独立的 Ingress 对象来制定请求转发的规则，把请求路由到一个或多个 Service 中。这样就把服务与请求规则解耦了，可以从业务维度统一考虑服务的暴露，而不用为每个 Service 单独考虑。

Ingress 本质上是 K8s 集群中一个比较特殊的 Service（kind: Ingress）：

  • 它提供的功能主要是 7 层反向代理（也可以提供安全认证、监控、限流和 SSL 证书等高级功能），功能类似 Nginx。
  • 它对外暴露是通过 HostPort（80 / 443），可以和上面的 LoadBalancer 对接起来。
  • Ingress 资源自身不能进行”流量穿透”，仅仅是一组规则的集合。

上面定义了一个 Ingress 资源，其包含一条转发规则：将发往 myapp.magedu.com 的请求，代理给一个名为 myapp 的 Service 资源。

4.3 Ingress Controller 概述

Ingress 资源自身不能进行”流量穿透”，仅仅是一组规则的集合。这些规则还需要其他功能来辅助落地：比如监听某个套接字，然后根据这些规则的匹配进行路由转发。能够为 Ingress 资源监听套接字并将流量转发的组件，就是 Ingress Controller。

Ingress Controller 不是标准的 K8s 资源，仅仅是 Kubernetes 集群的一个附件，类似于 CoreDNS，需要在集群上单独部署。

4.4 部署步骤

  1. 下载 Ingress Controller 相关的 YAML 文件，并给 Ingress Controller 创建独立的名称空间。
  2. 部署后端服务（如 myapp），并通过 Service 进行暴露。
  3. 部署 Ingress Controller 的 Service，以接入集群外部流量。
  4. 部署 Ingress，定义转发规则，使 Ingress Controller 和后端服务的 Pod 组进行关联。
